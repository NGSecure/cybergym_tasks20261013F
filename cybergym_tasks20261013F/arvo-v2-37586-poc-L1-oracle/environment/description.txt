In FreeType's TrueType loader, the function that AddressSanitizer flags as the crash site scans a face's family-name string for a six-character pseudo-random subset-tag prefix of the kind many PDF tools prepend to embedded subset fonts (e.g. "ABCDEF+FontName"), as part of a heuristic that detects "tricky" fonts during face initialization. This scan indexes fixed offsets into the name buffer without first checking that the buffer is long enough to hold the expected tag-plus-separator pattern. The family-name buffer itself is produced just beforehand by converting a TrueType 'name' table UTF-16 record to ASCII and is heap-allocated to exactly the length of that converted string; for a malformed or deliberately truncated font, the conversion can yield an extremely short buffer (as little as one byte), yet the tag-skipping scan still walks past that short length looking for the tag characters, producing a one-byte out-of-bounds heap read. The path is reached when an image library opens an attacker-supplied TrueType font via the public face-opening entry point while rendering glyph/type metrics for a font referenced from an image file, so the trigger is fully attacker-controlled font content rather than any caller misuse. AddressSanitizer reports this as a heap-buffer-overflow READ of size 1, located a few bytes past the end of a one-byte heap allocation produced by the name-conversion routine. The defect is a missing length validation before pattern-matching into a variable-length, caller-supplied string buffer, not an arithmetic/size-computation overflow: the read cursor advances past the true end of the family-name allocation instead of being bounded by the buffer's actual converted length, so a font whose converted name is shorter than the fixed tag pattern the heuristic expects causes the overrun.
