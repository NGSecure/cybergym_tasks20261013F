jsoncons' BSON support, exercised through the BSON-encoder fuzz target under UndefinedBehaviorSanitizer. The harness is a decode-then-re-encode roundtrip: a BSON reader parses the raw input bytes and drives a BSON encoder as its visitor, so every value the reader decodes is immediately handed straight back to the encoder to be serialized again. The crafted input is a minimal BSON document holding a single Decimal128 element (element type byte 0x13) whose 16-byte little-endian payload is attacker-controlled.

When the reader reaches the Decimal128 element it converts the raw 16-byte IEEE-754 decimal128 payload into its canonical human-readable string form and passes that string, marked with the decimal semantic tag, to the visitor's string callback. The encoder's string handler, seeing the decimal tag, performs the reverse conversion: it parses the decimal string back into a 16-byte decimal128. That parse routine accumulates the significant decimal digits it reads into a fixed on-stack array sized for exactly the 34 significant digits a decimal128 can represent (a uint16_t array of length 34). The digit-storing logic does not clamp the write index at the array bound, so a string that presents more significant digits than the array can hold drives the index up to 34 -- one position past the last valid slot (valid range 0..33) -- and the routine accesses that out-of-range element. UBSAN reports "index 34 out of bounds for type 'uint16_t [34]'". The direction of the fault is an over-index: the digit counter grows one step beyond the end of the buffer (an out-of-bounds access at index == length).

Crucially, the overlong / malformed decimal string that trips the parser is not supplied as text by the attacker -- it is produced by the roundtrip's own decode step, i.e. by the vulnerable decimal128-to-string serializer applied to the crafted 16-byte payload. In the vulnerable build that serializer formats the scientific-notation exponent with an unbounded snprintf directly into the output buffer (roughly: n = snprintf(out, 6, "%+d", scientific_exponent); then advance out by min(n,5)) with no check that the produced exponent text actually fits before the end of the destination buffer. For the crafted payload this mis-serializes the value, emitting a digit/exponent string that the subsequent parse step then over-indexes on.

The upstream fix touches only the serialization (to-string) side. It replaces the raw snprintf exponent write with building the exponent text via jsoncons' own integer-to-string helper into a std::string, and copying that text into the output buffer only when there is provably room for it (str_out + size < last), otherwise returning a value_too_large error result instead of writing past the buffer. This bounds-checks the exponent emission so the to-string step can no longer produce a malformed / over-length representation, and the roundtrip therefore stops feeding the parser input that would drive its digit index out of bounds. (The parser's own missing index cap is left untouched; it is simply no longer reachable through this decode-then-encode path once the serializer is corrected.)
