LibreDWG's DXF importer (fuzz target: llvmfuzz, ASan build) crashes during final heap teardown after parsing a crafted DXF TABLES section, because an earlier type-confusion bug in a table-control post-processing step let a non-BLOCK table object be reinterpreted and mutated as if it were the BLOCK table's control object.

Crash mechanism: DXF's TABLES section can declare several different table kinds (e.g. LTYPE, VPORT, APPID, BLOCK, LAYER, DIMSTYLE, STYLE, VIEW, VX, UCS, BLOCK_RECORD, BLOCK_HEADER are all accepted table names). After each such table's entry group is parsed, the importer runs a generic "no NULL entries" cleanup pass over that table's control object. This pass unconditionally reinterprets the control object's tagged-union payload through the BLOCK-control variant and reads its entry-count/entry-array fields via that view, without first checking that the control object's actual dynamic type really is the BLOCK-control type. When the DXF input instead declares some other table kind from the accepted-name list, the union slot in fact holds a differently shaped, differently sized control struct for that other kind, so the entry-count and entry-array values read out are just whatever bytes happen to sit at those offsets in the real (mistyped) struct -- an attacker-influenced, effectively garbage count paired with a garbage/wild pointer. The cleanup loop then walks that bogus array from the end backward: for a NULL slot at the trailing end it just shrinks the (bogus) count, but once a non-NULL slot has been seen, any NULL slot encountered after that point (i.e. a hole preceding a later real entry, not a trailing one) instead writes a freshly-built handle reference into that slot through the wild pointer, silently corrupting heap allocator bookkeeping (chunk metadata / redzones) rather than crashing immediately. The corruption only surfaces much later, at the very end of the run, when the whole parsed object graph is torn down: freeing one of the real BLOCK objects' per-type private data passes an address whose allocator-tracked state was clobbered by that earlier wild write, so the sanitizer's own internal atomic bookkeeping operation dereferences a bogus, out-of-range address and the process dies with a SEGV (WRITE) deep inside the sanitizer runtime instead of with a clean "invalid pointer passed to free" diagnostic -- a classic corrupt-now-crash-later pattern, which is why the reported crash site is inside allocator/quarantine internals rather than at the actual site of the type confusion.

Fix verification: the patch adds a guard requiring the control object's fixed type to actually equal the BLOCK-control type before the entries-cleanup pass is allowed to run, so the pass is now skipped for every other table kind instead of misinterpreting their control structs through the BLOCK-control view. This directly closes the type-confusion window described above, and is consistent with the accepted-table-name list including many non-BLOCK table kinds that previously all fell through the same unguarded code path. fix_commit_plausible: YES -- the upstream OSS-Fuzz record for this exact testcase lists an identical three-frame crash signature ending in the same object-teardown/free path, and ClusterFuzz independently marked that testcase "verified as fixed" once a build containing this commit was in place; the commit's own message additionally describes adding extra type protections to this same table-parsing routine for illegal/fuzzed input, matching the mechanism inferred from the crash trace's allocator-internal frames.
