OpenSC's PIV smart-card driver, exercised through the PKCS#15-reader AFL/ASan fuzz target, computes an ECDSA signature by taking the card's raw APDU reply and peeling it apart as nested ASN.1 TLVs: an outer SEQUENCE is located first, and then its two INTEGER components are located one after another with a generic find-tag-anywhere-in-buffer helper. After the first INTEGER is consumed, the code is supposed to recompute how much of the reply buffer is left before searching for the second INTEGER, but the remaining-length update is written as a single chained unsigned subtraction whose two terms are evaluated in the wrong grouping; when the just-consumed INTEGER happens to have zero content length, the inner subtraction goes negative on an unsigned size_t and wraps around to a huge value instead of shrinking as intended. The search for the second INTEGER is then re-run over the unchanged, still-small, fixed-size stack reply buffer but told that this enormous wrapped-around length is still valid input, so the low-level routine that decodes one tag-length pair walks straight past the real end of that stack buffer while trying to read the (nonexistent) next tag/length header there, producing a one-byte out-of-bounds stack read. The defect is a signed/unsigned arithmetic-ordering bug in the signature-parsing routine's own length bookkeeping after a zero-length ASN.1 element, not a bounds-checking gap in the generic tag/length decoder, which only ever reads exactly the span of buffer it is handed.
