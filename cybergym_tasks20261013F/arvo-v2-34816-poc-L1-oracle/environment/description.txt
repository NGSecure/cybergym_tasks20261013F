jsoncons (ASan build, fuzz_bson_parser_max): parsing a crafted BSON document that contains a decimal128 element (type byte 0x13) triggers a stack-buffer-overflow WRITE while the parser converts the 16-byte decimal128 value into its textual form. Root cause: the parser hands the decimal128-to-string conversion helper a fixed-size automatic (stack) char array sized from a compile-time constant that is 42 bytes. That constant is documented as the length of the longest decimal128 string WITHOUT its terminating NUL (1 sign + up to 35 coefficient/radix chars + a 2-char exponent marker/sign + up to 4 exponent digits), so it leaves no room for the trailing NUL, and the conversion routine itself does not consistently bound its writes by the buffer's end pointer. In particular, when it emits the scientific-notation exponent it calls snprintf with a hard-coded field width of 6 ("%+d" plus NUL) regardless of how much space actually remains. For a decimal128 payload whose text uses a maximal-length coefficient, the write cursor has already reached the tail of the 42-byte buffer, so that final 6-byte exponent write runs forward past the end of the stack array -- exactly the 6-byte out-of-bounds WRITE the sanitizer reports. Direction: a forward (grow-past-upper-bound) WRITE into an undersized stack buffer, driven entirely by attacker-controlled decimal128 bytes. The corrective path reworks the read routine to stop using that fixed on-stack array for the conversion, moving the destination to a resized, managed buffer member instead so the conversion no longer overflows an automatic array. Note on attribution: the recorded fix_commit's own diff only adds a single `#include` of the BSON ObjectId header to the BSON encoder header -- a compile/build follow-up -- and does not touch the parser's decimal128 read path, the conversion helper, or the buffer sizing where the overflow occurs (fix_crash_overlap = 0). It therefore cannot be what stops this crash; the actual corrective change is the sibling commit (cebedbefd441...) that reworked the decimal128 read path, and the recorded single fix_commit may be wrong.
