Draco's point-cloud decoding path (reached through the honggfuzz point-cloud-decoding entry point that skips re-quantization, built with an address sanitizer) reconstructs each decoded point attribute's component values using a per-attribute prediction scheme chosen by the bitstream. One such scheme exists specifically for two-component texture-coordinate attributes: whatever the actual geometry, it always predicts exactly two output values per point and writes them into two hard-coded result slots, while the small working buffer that holds those result slots is sized according to the component count the attribute itself claims to have — a number the decoding side trusts from the stream rather than verifying against the scheme it is about to apply. When a corrupted input selects this texture-coordinate-specific prediction scheme for an attribute whose declared component count is not two, the working buffer ends up allocated with fewer than two elements while the prediction routine still unconditionally fills both of its fixed result slots, so AddressSanitizer catches the second of those two writes landing past the end of the undersized heap allocation. Root cause: the two-component texture-coordinate prediction decoder never checks that the attribute it has been handed actually has two components before performing its two hard-coded result writes, so an attribute/prediction-scheme mismatch in the bitstream turns a fixed-size write into a heap-buffer overflow.
