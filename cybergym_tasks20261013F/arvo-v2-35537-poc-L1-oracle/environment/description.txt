c-blosc2's fuzz target for frame decompression begins by handing an arbitrary input blob to the library's super-chunk-from-buffer constructor, which wraps the raw bytes into an in-memory frame/super-chunk object and goes on to decompress its chunks without first checking that the blob actually begins with the fixed signature every super-chunk header built by the library itself is guaranteed to carry. Because that check is missing, a blob that is not really a valid frame at all is still accepted, and whatever bytes happen to sit at the offsets the parser expects a chunk's declared compressed-size field to occupy are trusted as if they were genuine. For one of the chunks, that untrusted size value is larger than the amount of data actually left over in the host buffer (which was only ever allocated to the length of the fuzzer's input), and it gets passed straight through as the source-length argument to the selected codec's decompression call. When the codec selected for that chunk is zstd, this value reaches the bundled zstd decoder's frame parser, whose raw-block handling copies exactly the number of bytes it was told to trust directly out of the host buffer -- overrunning the real, much smaller allocation and producing a heap-buffer-overflow READ. The bundled zstd code is not itself defective here: it is given a length that is internally self-consistent within the (bogus) frame it was asked to decode, and it simply copies that many bytes from the buffer it was pointed at; the actual defect is upstream, in c-blosc2's own frame-ingestion path accepting an unverified buffer as a legitimate compressed frame and letting its self-reported size metadata flow, unchecked against the real buffer length, all the way down to the copy.
