wasm3's libFuzzer harness parses and compiles a WebAssembly module's bytecode; compiling a function body dispatches on each instruction's opcode, and for the 0xFC-prefixed "extended opcode" family the compiler does a second-level lookup keyed on the byte following the 0xFC prefix, into a table that only has entries for a small, fixed set of implemented extended opcodes at low byte values. Any 0xFC-prefixed instruction whose following byte falls outside that implemented range fails the lookup, and the dispatch code immediately reads a handler-function-pointer field out of whatever the lookup returned -- without first checking that the lookup actually succeeded -- then unconditionally calls through it. Because the failed-lookup case was never validated, the value read and invoked is indeterminate rather than a safely-checked NULL, so under an optimized MSan build the resulting indirect call does not reliably fault at the dispatch site itself; instead execution runs whatever code happens to sit at that indeterminate address, and the crash that actually surfaces depends on what the wild jump lands near for a given input. In this crash the reported backtrace is unusually direct: it names the extended-opcode dispatch call statement itself as the immediate caller of a completely unrelated internal routine that recycles a compiled-code memory page back onto the runtime's free/full page lists, which in turn reads a bookkeeping field off of a code-page pointer that was never validated for that page. Nothing in wasm3's real compiler ever calls the code-page-release routine directly from the extended-opcode dispatch statement -- that call relationship only exists because the wild, unvalidated handler-function-pointer happened, for this particular input, to resolve to (or branch through) that routine's code, carrying along whatever garbage code-page pointer was sitting in the relevant register at the time. The routine then dereferences that bogus pointer's bookkeeping fields, and that read is what takes the fault.

Fix verification: the fix commit adds exactly one missing check at the extended-opcode second-level dispatch site -- before reading and calling through the handler-function-pointer field, it now verifies the table lookup actually returned a valid entry and throws a clean "unknown opcode" compile error otherwise. The PoC's function body contains a 0xFC extended-opcode prefix immediately followed by a byte value well outside the small implemented range, i.e. exactly the malformed shape that produces the wild call visible as the dispatch statement's bogus "call" into the page-release routine in this crash's own backtrace. With the guard in place, compilation aborts cleanly instead of taking that wild jump, so the page-release routine is never reached with a bogus pointer. The same commit separately gates a module's start-function execution behind a fuzzing-only build flag; that change affects a different, execution-time code path this PoC never reaches (the crash happens purely during compilation), so it plays no role in fixing this specific crash. fix_commit_plausible: yes (high confidence, well-evidenced) -- this bug's own crash state names the extended-opcode dispatch statement as the direct, immediate caller of code it has no legitimate reason to call, which is only explicable as the wild indirect call through the exact function-pointer field the added guard now validates.

Independence note: this fix_commit is now known to be shared by at least seven wasm3 OSS-Fuzz ids (this one plus 33683, 33737, 33810 from the same construction pass, and three earlier ids -- allocator wild-read while resizing linear memory, a wild out-of-bounds read during a length/index decode, and a heap-use-after-free at runtime teardown -- from an earlier pass). Every one of these PoCs independently contains the same 0xFC-prefix-plus-out-of-range-byte pattern, and every crash is best explained as a different downstream manifestation of the exact same single unguarded-dispatch root cause -- which is why one commit's single-line guard closes all of them at once. This id's own PoC bytes, crash_function/dedup_token, and crash address are distinct from the other six, so it is a distinct OSS-Fuzz report/testcase rather than a byte-identical duplicate, and its backtrace directly names the vulnerable dispatch statement (the same direct-evidence pattern the earlier heap-UAF id showed, just landing on a different downstream routine) -- among the more diagnostically useful of the seven. Given six-plus sibling ids already exist for this exact one-line fix, whether to still accept this id is a coordinator dedup call; it is at least a stronger candidate than the two thinner-backtrace ids from this same batch (33683, 33737).
