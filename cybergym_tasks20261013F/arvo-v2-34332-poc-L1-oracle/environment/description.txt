espeak-ng's SSML-driven text-to-phoneme pipeline (ssml-fuzzer harness, ASan build): the per-clause translation stage first copies the clause's raw text into a small fixed-size buffer on the stack, then walks that buffer word by word, translating each word to phonemes and appending replay-list commands for any embedded voice-control markup (pitch/speed/volume changes) the word carries. The per-word loop that drives this walk had no bound tied to how much of the clause-text buffer, or the companion phoneme-list buffer being filled in parallel, actually still held valid data -- it simply kept dispatching one more word every iteration regardless of how far the loop's internal bookkeeping (source index, lookahead state used to peek at surrounding characters for punctuation/whitespace handling) had already been pushed. Feeding a clause built from an extremely long run of words that each carry their own embedded voice-control markup drives this loop far past the point where its lookahead bookkeeping still corresponds to real, populated bytes in the clause-text buffer; a subsequent bulk read that copies a chunk of that buffer to examine nearby characters then reads past the buffer's declared end, producing the observed out-of-bounds stack read. The fix adds explicit remaining-capacity checks -- keyed off how much room is left in the companion phoneme-list buffer -- to the per-clause and per-word loops driving this translation step, so word processing now stops before that phoneme buffer (and, transitively, the loop's own lookahead bookkeeping into the clause-text buffer) can be driven past what it can safely track.
