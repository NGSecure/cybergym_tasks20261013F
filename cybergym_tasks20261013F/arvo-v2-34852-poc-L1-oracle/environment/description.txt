Root cause: a COLRv1 glyph-to-paint offset is resolved against the wrong base address during table validation.

HarfBuzz's COLOR (COLRv1) table represents each "base glyph" entry as a small fixed-size record (a glyph id plus a 32-bit offset) stored in a sorted array. Per the OpenType COLRv1 spec, that offset is meant to be measured from the start of the array/list that holds all of these records, not from the start of the individual record itself. Before the fix, the record's own validation routine resolved and bounds-checked this offset using the record's own address as the base, instead of the address of the enclosing array. Because successive records in the array live at increasing addresses, the "record-relative" and "array-relative" readings of the very same stored offset value point at different byte ranges inside the font blob.

That base mismatch meant the one-time structural validation pass approved an offset whose target address did not match the address the real traversal code computes later. When the font-subsetting path walks the COLRv1 paint graph (closure computation over the paint table, reached from the base-glyph list while building the retained-glyph set), it recomputes the referenced paint sub-table's address using the array as the base — the spec-correct interpretation — but that address was never checked by the earlier, record-relative validation. For a crafted/corrupted font where this discrepancy pushes the real target past the end of the sanitized font blob, even reading a single byte from the paint sub-table's header (via the generic big-endian integer accessor used for small fixed-width fields) lands outside the mapped/validated memory, producing the out-of-bounds read reported here. The faulting access is a plain READ: the offset value itself is attacker-controlled font data rather than some internally degraded/truncated value, and nothing is corrupted or written — only the base used to turn a plausible-looking stored offset into an actual memory address disagrees between validation time and use time, so an offset that is out-of-bounds under the correct (array-relative) interpretation can still pass validation under the incorrect (record-relative) one.

The real fix removes this precondition by threading an explicit base parameter — the enclosing array's address — through the record's validation routine, so it is used both for bounds-checking the record's own offset and for validating whatever the offset points at, and the enclosing array/list gains a validation entry point that supplies itself as that base. With a single, consistent base used at validation time and at later traversal time, an offset that only appeared in-bounds under the previous (wrong-base) interpretation now fails validation up front, so a malformed font is rejected before the paint graph is ever walked and the later traversal never reaches an address outside the validated region.

fix_commit assessment: the fix commit's diff is confined entirely to the base-glyph record type and its enclosing list/array — exactly the component that supplies the offset which is resolved and read deeper in the paint-dispatch traversal shown in the crash backtrace. There are no unrelated hunks. This is consistent with the fix addressing the true root cause (the base-address mismatch) rather than being a merely time-correlated or cosmetic change.
