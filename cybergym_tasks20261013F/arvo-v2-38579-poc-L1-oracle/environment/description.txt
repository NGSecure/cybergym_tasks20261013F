libucl's UCL-document parser, exercised through the "parse a string into an object" fuzz entry point (ASan build), crashes with a heap-buffer-overflow READ of 8 bytes while computing a hash over an object key. The crash surfaces deep inside the generic string-hashing routine used to place keys into an object's internal hash table, which reads its input in machine-word-sized chunks according to a caller-supplied length.

Root cause is upstream of the hashing call, in the code path that handles object inheritance during parsing (one object's properties being derived/merged from another already-parsed object). That path deep-copies the source object, including duplicating its key text into a fresh heap buffer. The source key, however, is not a plain NUL-terminated C string — it is a raw slice of the parser's internal scratch storage, whose true length is tracked separately as an explicit byte count on the object. The duplication step nonetheless treated it as a C string, scanning for a terminating zero byte to decide how much to copy/allocate. Because the scratch buffer can legitimately contain a zero byte before the key's real end, the duplicated copy can end up allocated shorter than the key actually is, while the separately-tracked length field on the new (copied) object is left unchanged, still reflecting the original, longer size.

When the copied object is then inserted into its parent's hash table, the hash routine is handed the copied key pointer together with that stale, longer length and reads the key in 8-byte-aligned chunks up to that length. Since the real allocation backing the copy is smaller (7 bytes here) than the length being read, the last word-sized read strides past the end of the heap block, producing the observed 8-byte out-of-bounds read immediately adjacent to the allocation. This is a read-side overflow driven by an undersized allocation (the copied key buffer shrank relative to the object's recorded key length), not a growth/overflow-on-write bug.

fix_files is non-empty, so the patch was read. It modifies exactly the object-copy routine identified by the allocation-site stack trace. Instead of duplicating the source key with a NUL-scanning string-duplication call, the fix first clears the destination's copied-key storage, and only when the object's key actually aliases that scratch storage does it allocate a buffer sized to the object's own recorded key length and copy exactly that many bytes into it (a fixed-length allocate-and-copy rather than a scan-until-zero duplicate). This guarantees the copied buffer's real allocation size always matches the length that will later be handed to the hash routine, eliminating the size mismatch that produced the out-of-bounds read.

fix_commit judgment: the recorded fix commit is very likely correct. Its diff touches only the single function that appears as the allocation site in the crash report's "allocated by" stack (the object-deep-copy routine reached via the inheritance handler during parsing), and the change directly repairs the exact mismatch this crash depends on — replacing a NUL-terminated duplication of a non-NUL-terminated, explicitly-length-tracked key with a length-exact allocate/copy. No other candidate location in the reported stack (the hashing routine itself, the hash-table lookup, or the state-machine dispatch) is modified or would need to be for this bug to be resolved, so the fix commit matches the crash.
