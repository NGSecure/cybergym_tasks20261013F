libexif's EXIF-data parser, exercised through the exif-from-data fuzz entry point (ASan build), when it walks the Apple vendor maker-note block attached to a JPEG/TIFF EXIF segment and formats each maker-note tag entry into a human-readable string for the caller. For a tag entry whose declared type is an (unsigned) rational -- a numerator/denominator pair, each half a 4-byte integer -- the formatter hands the tag's raw value bytes straight to the library's shared byte-buffer-to-number conversion helpers: one routine decodes a 4-byte big/little-endian integer, and a routine built on top of it pairs two such 4-byte reads together into a numerator and a denominator. Nothing before that handoff checks that the maker-note entry's backing value buffer is actually large enough to hold the 8 bytes a rational value requires, nor that the entry declares at least one component -- the formatter only trusts the tag's declared component count and type tag, not the size of the buffer that was really allocated for its value when the maker-note's internal entry table was built. A maker-note entry that claims to be RATIONAL-typed but whose actual backing allocation is only one byte is passed straight into this decode path; the first 4-byte integer read already overruns that tiny allocation, landing two bytes past its end and triggering a one-byte heap out-of-bounds read deep inside the shared integer-decoding helper -- the same low-level helper used for ordinary (non-rational) integer-typed tags, reached here one extra call frame down because a rational value is decoded as two chained integer reads rather than directly.
