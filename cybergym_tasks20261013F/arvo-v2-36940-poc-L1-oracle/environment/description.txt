SerenityOS's LibGfx BMP image decoder, exercised through the same BMP-loading fuzz entry point, UBSan build: for the oldest (CORE-header) bitmap revision, the loader first reads the file's indexed color table, sizing its expectation from the bit depth the CORE header declares -- e.g. a header claiming enough bits per pixel to need sixteen palette entries expects a specific, correspondingly larger number of color-table bytes. If the file actually supplies fewer bytes of color-table data than that declared bit depth calls for, the loader logs a one-line warning about the shortfall but, rather than rejecting the file outright, proceeds anyway with whatever truncated -- here, effectively empty -- color table it managed to read. Decoding then moves on to the pixel data, which for this file is run-length-encoded; unpacking an RLE-coded row repeatedly maps each decoded byte to a slot in the output pixel buffer using an index derived from the (now undersized) color-table state, and when that derived index runs past the end of the buffer, the RLE unpacker's bounds check rejects the byte and, on that path, prints a second, fixed diagnostic string carrying no runtime substitution values. As with any such zero-argument call into the project's formatted-logging machinery, that print instantiates a zero-length internal argument-container object and then invokes a member function on it, which Clang 16 combined with UndefinedBehaviorSanitizer flags as a call into an object that lacks enough storage for its own declared type. The crash itself sits in that always-present logging path, reached here only because the earlier under-populated color table let the RLE unpacker's index arithmetic drift out of range in the first place.
