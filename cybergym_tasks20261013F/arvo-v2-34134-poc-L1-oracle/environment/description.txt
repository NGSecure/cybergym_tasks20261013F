PCL's PLY point-cloud loader, exercised here through a fuzz harness that feeds arbitrary PLY files into it, fills a flat, pre-sized byte vector inside a point-cloud container object as it walks the header's declared field list, tracking where to place each field's value on the current point row as a running byte offset carried across successive per-property callbacks. When the parser hits a scalar vertex property, it copies the property's raw bytes straight into that vector at position = row_index * row_stride + running_offset via a direct memcpy — the same unconditional pattern is used for the vertex-color, vertex-alpha, vertex-intensity and generic list-content callbacks. None of these sites ever verifies that position plus the value's size still lies inside the vector. Because row_stride and the row count were themselves derived earlier from the same untrusted header (the allocation is sized once, right after the header section ends), a PLY input whose declared property list yields more bytes per row than that allocation actually reserves — extra or duplicate scalar properties, or a property list whose accumulated size doesn't match what the header advertised — lets the running per-row offset on the final row walk past the end of the vector. Because the scalar value is deposited by a raw memcpy at that out-of-bounds position, the parser performs a 4-byte WRITE immediately past the end of the heap-allocated buffer rather than a load, landing squarely in the ASan red zone adjacent to the vector's last live byte.

The fix does not touch how the byte-vector's size or the per-row stride get computed; instead it removes the blind trust placed in an offset derived from attacker-controlled header metadata before that offset is used to touch memory. It adds a bounds-checked element accessor on the point-cloud container — templated on the stored type, taking a row index and a byte offset — that recomputes the identical position and throws an out-of-range exception whenever position plus the value's size would exceed the vector's current size, instead of ever indexing past it. The vertex-property callbacks that previously did the raw memcpy are all switched to this checked accessor; the scalar-property, list-content and color callbacks wrap it in a try/catch that logs a warning and abandons that one value rather than writing out of bounds, while the alpha and intensity callbacks use the same checked accessor but without a surrounding try/catch (an out-of-range there throws rather than being swallowed). The loader's post-parse pass that backfills unwritten rows or duplicates rows for a range grid gets the same treatment: every place that computed a destination or source index from row/point-step arithmetic and handed it straight to a raw memcpy/memset now explicitly checks that index plus the copy length against the buffer's size and aborts parsing (returns failure) instead of touching memory outside it. The mirrored ASCII-output helpers on the writer side are switched to the same checked accessor in place of a separately, and inconsistently, recomputed per-row byte size that had been used to index into the buffer for output — removing a second, independent spot where a stale row-size value could produce an out-of-bounds index. Net effect: the precondition the crash relied on — an offset built from untrusted, header-declared property counts/types being trusted to land inside a buffer sized from that same header, with no runtime check at the point of the write — is closed off; a malformed header now degrades to a logged warning or a parse failure instead of an out-of-bounds heap WRITE.

The recorded fix commit is a precise match for this crash: the hunk that replaces the raw memcpy in the scalar vertex-property callback (the exact crash site) with the new checked accessor is part of this same commit, and the commit's touched files/functions line up exactly with the ones recorded for this id. Directionality also checks out: the crash detail (WRITE of size 4, at an address 0 bytes past a 116-byte allocation) matches a scalar property's value being deposited just past the end of the point-cloud's byte buffer — a forward heap-buffer-overflow WRITE on the container's data vector, not a load and not an underflow — consistent with the running per-row offset exceeding the span reserved for that row.
