Project: libexif, exercised via the EXIF loader pulling a vendor-specific MakerNote sub-record out of a crafted image. ASan reports a SEGV ("wild-addr-read") inside a low-level bulk-copy routine, reached while the library loads Exif data and dispatches the maker-note payload to its Apple-vendor sub-parser.

Mechanism (re-derived from the crash trace and the vulnerable source, not copied from the crash fields): the Apple-vendor MakerNote sub-parser walks the MakerNote payload as a table of fixed-width tag entries. For each entry it reads, straight out of the untrusted buffer, a 2-byte "format" code and a 4-byte "component count" field, then computes that entry's payload size as the format's byte-width multiplied by the component count, using ordinary fixed-width unsigned arithmetic (no widening). Because the component count is taken verbatim from attacker-controlled bytes and can be any value across its full range, this multiplication can wrap around: a deliberately oversized component count paired with a particular format code yields a product that wraps back down to a small number instead of reflecting the true, enormous requested size. The code then checks that computed size against a fixed cap and against the overall input length — but since the value being checked is the already-wrapped, deceptively small number, a corrupt entry that should have been rejected sails straight through. That same wrapped-small size is then used both to size the newly allocated per-entry buffer and as the length to copy from an attacker-controlled offset inside the shared input buffer. A second guard checks that offset-plus-size still stays within the input buffer, but that check is likewise ordinary fixed-width addition and can itself be satisfied even when the offset is effectively enormous (interpreted as unsigned), because offset+size again wraps back into range. The net effect is that the copy's source pointer is built from an offset that was never genuinely validated, so the read walks off into unrelated or unmapped memory — the observed wild-address SEGV. Direction: a READ, on the copy's source side (the shared input buffer plus an unvalidated offset), not the freshly allocated per-entry destination. The degenerate quantity is the wrapped multiplication product, not a sign/negative-length issue.

Fix: the upstream fix inserts a division-based, overflow-safe pre-check — evaluated before the vulnerable multiplication is performed at all — that rejects, and stops processing the rest of the entry table outright (rather than merely skipping ahead to the next entry), any entry whose true, non-overflowed size would already exceed the input length. This closes the wraparound before it can ever reach the later size/offset checks. The existing "size too large" guard immediately after is likewise hardened to abort the whole table walk instead of continuing past a corrupt entry.

fix_commit judgment: the recorded fix commit is a correct, minimal, single-hunk match directly on the crash's own parse path — it adds exactly the missing overflow guard ahead of the size computation that the trace shows executing, with no unrelated changes. This bug, and its fix, are distinct from the other Apple-MakerNote libexif ids built in this batch, each closed by its own different commit: one sibling's bug was a *missing* bounds check on the offset-plus-size pair used for this very copy step (fixed by an earlier, separate commit that added that check) — this task's bug is specifically the integer-overflow route that can still bypass that already-present check by making the checked size look small when it is not. Another pair of sibling ids closed an unrelated defect: an up-front table-size sanity check that undercounted the real per-entry stride, letting the parse cursor itself run too far, with no multiplication overflow involved at all. All three fixes touch different mechanisms within the same parser and are not interchangeable with this task's commit.
