Project: libexif, exercised through its EXIF/MakerNote parser on a crafted image. ASan reports a 1-byte heap-buffer-overflow READ.

Mechanism (re-derived from the crash trace and the vulnerable source, not copied from the crash fields): the loader for Apple-brand MakerNote data treats the MakerNote blob as an IFD-like table of fixed-width entries. Before walking the entries it performs a single up-front sanity check that the table fits inside the MakerNote buffer, but that check computes the table's byte span using the WRONG per-entry stride: it multiplies the attacker-controlled entry count by 6 bytes per entry, whereas the actual per-entry walk in the parse loop advances the cursor by 12 bytes per entry (the real on-disk entry width). Because the declared-size check undercounts by half, a crafted entry count that is really too large to fit still passes the guard. The subsequent loop then steps 12 bytes per entry through the buffer and, on an entry whose derived data pointer sits at the very end of the allocation, the low-level 16-bit value accessor dereferences one byte beyond the end of the MakerNote source buffer — the observed out-of-bounds READ. Direction: a READ past the end of the (source) MakerNote input buffer, caused by an under-counted size check letting the parse cursor run past the allocation; no write, and the degenerate quantity is the mismatched stride (6 vs 12), not a wrapped/negative length.

Fix: the upstream fix corrects the up-front bounds check to use the true 12-byte-per-entry stride (and includes the base data offset), and additionally adds a per-iteration guard inside the parse loop that stops before an entry whose offset+width would exceed the buffer size — so both the aggregate check and each individual entry access are now bounded by the real buffer length. fix_commit judgment: the recorded fix commit is a correct, minimal, single-hunk match — it rewrites exactly this stride-miscount check plus the per-iteration bound, directly on the crash's own parse path, and is distinct from the sibling libexif task in this batch (a different Apple-MakerNote offset/size bug closed by a different commit).
