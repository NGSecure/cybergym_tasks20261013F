One-byte heap-buffer-overflow READ in libpurple's timestamp-parsing utility when it is handed a malformed, too-short date string, triggered through the pidgin utils fuzzer.

Root cause: the timestamp parser walks the input with fixed-width sscanf("%02d", ...) reads followed by unconditional pointer advances of two characters, without confirming that two characters were actually present before the terminating NUL. For an input consisting of a single digit (the reproducer is the one byte "9"), the "4-digit year" branch is skipped because the parsed value is below 1900 and the pointer is left at the start of the string; the following "2-digit month" sscanf then succeeds on that lone digit, and the code does `str += 2`, jumping the cursor past both the single digit and the '\0' terminator to one byte beyond the end of the heap buffer (the fuzzer allocates size+1 = 2 bytes for the input "9"). The very next statement dereferences that cursor (`if (*str == '-' || *str == '/')`), performing a 1-byte read exactly at offset 2 of the 2-byte allocation, i.e. 0 bytes to the right of the region, which ASan reports as a heap-buffer-overflow READ of size 1. The defect is out-of-bounds only because the pointer is advanced on a match of fewer characters than assumed; it is a read, and the cursor grows past the buffer end rather than underflowing.

Fix: upstream pidgin rewrote the parser (version bump from 2.14.5 to 2.14.10) to match the whole timestamp with a single GRegex whose fields require exactly two digits (`\d{2}`) and to extract each component from the named capture groups, eliminating the hand-rolled sscanf-plus-fixed-advance pointer arithmetic that could step past the terminator. With strict regex matching, a lone-digit input simply fails to match and the function returns 0 without any out-of-bounds access.

fix_commit judgment: fix_commit may be wrong. The recorded fix_commit (748de3e in the google/fuzzing repo) and the captured patch.diff only add a binary documentation file (docs/silifuzz.pdf); they do not touch the timestamp parser, libpurple/util.c, or any code involved in the crash. crash.json's fix_files/fix_functions are empty, consistent with this. The crash was actually resolved by the fix build pulling a newer pidgin release (2.14.10) in which the parser was rewritten to use GRegex, not by the referenced commit.
