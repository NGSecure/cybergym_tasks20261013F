DuckDB's SQL parser builds its internal type representation by walking the parse tree produced for a CAST expression. When the target type is written as a composite (STRUCT) type with a list of "name TYPE" entries, the parser hands the type-building code, for each entry, a two-element list: the entry's name node and the entry's nested type node. The code consuming this pair reads the name node under the assumption — checked only by a debug-only assertion that is compiled out of the release/fuzzing build — that the node really is a string-valued parse node. It then takes whatever pointer is stored in that node's value union and immediately treats it as a C-string, copying it into a new string object. When the fuzzer drives the parser, through several layers of nested cast/expression transforms reached while building an UPDATE statement, into supplying an entry whose name slot is not actually the expected string-valued node kind, the value union instead holds unrelated leftover bits belonging to whatever other node type occupies that slot. Those bits are read as if they were a valid string pointer, and the resulting dereference lands on a wild, non-canonical address rather than anywhere near a real buffer. This independently confirms the crash's direction and nature: the trace's own "the signal is caused by a READ memory access" line and its wild-address-read classification both point to a read, and the access is a wild-pointer dereference produced by type confusion on a mistaken parse-tree node, not an index creeping past the end of a correctly-typed array by some incremental, bounded offset.

Patch review: the diff recorded against the labeled fix commit touches only an unrelated Java/JDBC native-library-loading helper (switching a load path to its absolute form). That file has no connection to the C++ parser, so it cannot be the actual security fix — the recorded fix-commit metadata does not correspond to the root cause here and should be treated as unreliable for this id. Comparing the vulnerable and "verified fixed" source snapshots directly instead (rather than trusting that commit), the real change is a substantial rewrite of the composite-type-name transform function: the previously debug-only check that the two-element entry list genuinely has two elements is promoted to a thrown parser exception, and the node-type check for the entry's nested-type half of the pair is likewise promoted from a debug assertion to a real runtime check, now enforced at the top of the function itself so it also covers the recursive call used for nested struct entries. Both changes remove preconditions that a malformed CAST target could previously exploit. However, the specific debug assertion guarding the entry's name half of the pair — the one whose bypass is what this particular crash exploits — reads identically in both the vulnerable and fixed snapshots; it remains assertion-only (and therefore unenforced in a release/fuzzing build) in the "fixed" snapshot too. The materials available here do not include the grammar/parser-generation sources that actually construct this entry list in the first place, so it cannot be confirmed from what's on hand whether the true elimination of this crash's precondition happened further upstream, in grammar productions that stop a malformed entry list from ever reaching this function, rather than in the transform function itself. This should be treated as an open point: the fix-commit mismatch is confirmed, and while the larger rewrite plausibly subsumes a fix for this exact crash by closing off the malformed input elsewhere in the pipeline, that specific line-level confirmation could not be made from the available materials.
