espeak-ng's SSML-driven text-to-phoneme pipeline (ssml-fuzzer harness, ASan build): while replaying the queued embedded voice-control commands (pitch/speed/volume changes) collected for a clause, the length-calculation stage walks a small, fixed-capacity global list one four-byte entry at a time, relying entirely on finding a distinguishing high bit set on the last entry of each word's batch to know when to stop -- it never checks its walking index against the list's own declared size. That list is filled while the clause's words are translated into phonemes one by one; while most of the call sites that append new entries to it do check remaining capacity before writing, at least one does not, and -- more importantly -- the loop that decides how many words in a clause get processed in the first place had no cap tied to how full either the (much larger) phoneme buffer or this smaller companion command list already was. Feeding a clause built from an extremely long run of words that each carry their own embedded voice-control markup lets the word-processing loop keep appending to the fixed-size command list far beyond what it can safely hold; the terminator invariant the replay loop depends on breaks down once the appended commands exceed what a batch of entries can correctly encode, and the replay loop then walks straight off the end of the 250-entry (1000-byte) global array, producing the observed 4-byte out-of-bounds read. The fix adds explicit remaining-capacity checks to the per-clause and per-word loops driving this translation step, tying how many further words/commands may be queued to how much room is actually left in the phoneme buffer, so processing now stops before either buffer -- and, transitively, the smaller companion command list -- can be over-filled.
