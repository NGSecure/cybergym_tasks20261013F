espeak-ng's SSML text-to-speech fuzz target (ASan build): spelling out a word letter-by-letter, where one letter needs to be voiced in a different ("alternate") language than the current voice, triggers a heap-use-after-free read while looking up that letter's phoneme-dictionary entry.

Root cause: espeak-ng keeps exactly one shared/global "secondary translator" object that many different code paths reuse whenever they briefly need to speak something in a language other than the active voice -- e.g. checking whether a bare letter can be pronounced by falling back to the default/English voice, or honoring an SSML-embedded per-word language override. The function that (re)points this shared object at a requested language first checks whether a secondary translator already exists for some *other* language; if so, it deletes (frees) that existing object before allocating and loading a fresh one for the newly requested language. The bug is that letter-by-letter translation is itself reentrant: an outer call sets up the shared secondary translator for one purpose (an embedded-language override for the current word) and starts reading dictionary entries through it, but resolving that same letter can recurse back into the letter-lookup logic for an unrelated inner check (the default/English-voice fallback test), and that inner check asks the very same setup function for a *different* language. Because the language differs from what is currently cached, the setup function frees the secondary-translator object the outer call had just built and is still relying on, then allocates a brand-new object for the inner check's language. When the inner check returns, the outer frame resumes and continues reading dictionary entries through what it still believes is its live secondary-translator object -- but that object was already freed by the reentrant inner call, so the dictionary lookup dereferences already-freed heap memory. This matches error.txt precisely: the freed-by trace shows the free happening deep inside a nested letter-lookup call (reached through a dictionary-rule-processing step) while an outer per-word secondary-translator setup call is still on the stack, and the previously-allocated-by trace shows the freed object was originally built by that outer per-word setup call, not by the inner one.

fix_commit note: patch.diff replaces the single shared secondary-translator global (and its cached-language string) with a small parameterized helper that takes the translator pointer and language-cache buffer as arguments, then re-exposes the original public setter as a thin wrapper plus adds a brand-new, independent *tertiary* translator object and its own wrapper. Every reentrant, per-letter fallback call site that previously reused the shared secondary translator is switched over to the new tertiary wrapper/object, so the per-word (outer) and per-letter-fallback (inner, reentrant) use cases each get their own dedicated translator slot instead of aliasing the same global. That directly removes the free-while-still-referenced condition described above: the inner reentrant check can no longer delete the object the outer frame is still reading from, because it now operates on a separate object entirely. The changed source locations (the translation-core function that owns the shared-secondary-translator setup logic, and the letter-lookup/letter-translation logic that performs the reentrant fallback check and was switched to the new tertiary API) line up exactly with the freed-by / previously-allocated-by / crashing-read call stacks in error.txt. fix_commit_plausible = yes, high confidence.
