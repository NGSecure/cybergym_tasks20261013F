PHP's Zend Engine, exercised through the php-fuzz-execute libFuzzer harness which simply compiles and runs an arbitrary PHP script buffer, crashes while running ordinary object-destructor logic at end-of-request shutdown. A PHP class can define a destructor that itself calls var_dump($this) and then unsets one of $this's own properties whose value is an array of child objects. Unsetting that array-valued property works by dropping the refcount on the array value currently held in the property's storage slot; when that drop takes the array's refcount to zero, the array is torn down immediately and synchronously, which in turn releases each element the array holds — and if one of those elements is the last reference to a child object, releasing it synchronously invokes that child's own destructor before the teardown call returns. If the child's destructor itself walks back up the object graph (e.g. it dumps a property that is, or contains, a reference back to the original object), it ends up re-reading the exact same property slot on the original object that is in the middle of being unset. The flaw is an ordering mistake in that unset routine: it released/tore down the slot's old array value first and only afterward marked the slot itself as empty, so during the reentrant window opened up by the nested destructor call, the slot still looks "live" and still typed as an array, pointing at a hash table that by now is partially or fully torn down. The reentrant object-dump walks into that stale array and indexes one of its already-freed elements, then dereferences the freed object's internal class-entry field — a heap-use-after-free read of a just-released small heap allocation (the freed object's own storage), consumed by the generic value-dumping code because the data it was handed turned out to be reading from a buffer whose owning container had already begun being freed one call frame up the same reentrant stack. The defect is squarely in the engine's core property-lifecycle/object-destruction bookkeeping (not a test-only or fuzz-harness artifact, and not a bug in the dumping routine itself, which only reads whatever property table it is given) — the fix is to clear the slot's own type/value to "empty" before releasing what it used to hold, so any reentrant access triggered mid-release observes an empty slot instead of a dangling live-looking one, closing the reentrancy window rather than changing anything about how the released data itself is freed.
