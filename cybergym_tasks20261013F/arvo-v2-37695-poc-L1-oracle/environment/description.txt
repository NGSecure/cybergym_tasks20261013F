PHP's Zend engine, exercised here through the standalone script-execution fuzz entry point (ASan build), crashes with a heap-use-after-free read while tearing down a Closure object immediately after a user-level function call completes. The closure involved wraps a synthetic "call trampoline": when a callable value that does not correspond to a real, already-compiled function -- for example an array-style [object, 'method'] callable resolved through Closure::fromCallable(), where the call must be dispatched through a dynamically-resolved or magic method -- is turned into something invocable, the engine builds a one-off internal function descriptor on the fly, allocates a private string holding the resolved method name for it, and wraps the whole thing in an ordinary refcounted Closure object so it can be passed around and called like any other closure. Destroying that Closure normally frees its private method-name string as part of tearing down the closure's internal storage once its refcount reaches zero. In the crashing input, the underlying trampoline-backed closure storage ends up being torn down twice within the same call-completion sequence: once when one reference to it goes out of scope as part of finishing the call, and a second time moments later when another reference -- which the engine still treats as pointing to a live object -- is also released and tries to tear the same storage down again. That second teardown re-enters the same free routine and reads/releases the method-name string that the first teardown already freed, producing the observed use-after-free read. The root defect is therefore a refcount/lifetime mismatch specific to trampoline-backed Closure objects: some path that creates, reuses, or forwards a reference to one of these synthetic closures does not keep that reference in sync with the object's real lifetime, so the generic closure-destruction logic ends up running twice against storage it already released the first time.
