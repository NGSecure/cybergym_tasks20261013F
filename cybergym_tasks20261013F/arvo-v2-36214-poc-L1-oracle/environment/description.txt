PHP's Zend engine fuzz target (ASan build): a heap-use-after-free read fires while resolving an array dimension assignment whose index is a non-integer value. When an array subscript is a float (or a resource) that does not map cleanly onto an integer key, the interpreter's slow-path index-conversion routine emits a diagnostic for the incompatible value before using it as the key. That diagnostic is routed through PHP's ordinary error-reporting machinery, which gives any user-registered error handler a chance to run arbitrary PHP code before the engine proceeds -- including code that reassigns or unsets the very variable holding the array currently being indexed. Nothing in the conversion routine re-checks the array's reference count after the handler returns, so if the handler's code was the array's last owner, the underlying hash table is torn down while the engine still holds a bare, now-dangling pointer to it; execution falls back out of the slow path and immediately dereferences that pointer to finish the assignment, producing the use-after-free read reported by the sanitizer. The root cause is an ordering bug, not a missing bounds check: converting an array index to a canonical key is treated as a side-effect-free operation, but on an incompatible scalar it can transitively invoke user code that frees the array out from under the very call stack performing the conversion.
