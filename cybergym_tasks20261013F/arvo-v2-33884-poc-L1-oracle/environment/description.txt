The Sleuth Kit's HFS+ filesystem-open path (fuzz target: sleuthkit_fls_hfs_fuzzer, ASan build): opening a crafted HFS+ image and computing the volume's highest inode number requires walking the on-disk catalog B-tree. Each catalog node is read into a heap buffer sized to exactly one node, and an index node is parsed by reading a trailing table of 16-bit record offsets to find where each record's key begins inside that buffer. The offset read from the table is validated to be less than the node size before it is trusted as a record start -- but the field read first at that offset is a 2-byte key-length value, and the check only guarantees one in-bounds byte at the offset, not two. A crafted node whose offset-table entry for the last record points at the very final byte of the node buffer therefore passes validation, and the subsequent 2-byte key-length read walks one byte past the end of the just-allocated heap buffer, which AddressSanitizer reports as a 1-byte heap-buffer-overflow read.
