Summary: A fluent-bit record-accessor value-translation path triggers a stack-buffer-overflow (an out-of-bounds READ) when a formatted numeric field is concatenated into the output string.

Root cause: The translation routine formats a numeric map value (an integer or a float) into a fixed 32-byte stack buffer using snprintf(str, sizeof(str) - 1, ...). snprintf returns the number of characters that *would* have been written had the buffer been large enough (the untruncated length), not the number of bytes actually stored. When a float value (formatted with "%f") produces a textual form of 32 or more characters, snprintf safely truncates the string into the 32-byte buffer but still returns the larger untruncated length (36 for the crashing input). That oversized length is then passed unchecked to the dynamic SDS string-append helper, whose internal memcpy copies that many bytes starting at the 32-byte stack buffer and reads several bytes past its end, causing the out-of-bounds stack READ. The bug is a degenerate/over-long-value case that bypasses the implicit "output fits in the buffer" assumption; it is a read overflow driven by the snprintf return value, not a write overflow. The fix adds a guard that, whenever the snprintf return length reaches 32, marks the field as not found and returns without performing the concatenation.
