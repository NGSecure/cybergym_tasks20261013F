dav1d, VideoLAN's AV1 video decoder, built with AddressSanitizer, crashes with a heap-buffer-overflow WRITE while applying the in-loop restoration post-filter during decoding of a crafted bitstream under the multithreaded fuzz harness. Before a frame is filtered, the decoder sizes a persistent scratch buffer that temporarily holds backed-up rows of reconstructed pixels for the restoration pass; the buffer's (re)allocation is gated solely by whether the per-row byte stride has changed since the previous frame, while the number of rows the buffer must hold is a separate quantity that depends on how many frame/tile worker threads are active for that frame. When a sequence of frames keeps the row stride constant but changes the effective worker-thread count (hence the row count the restoration stage must retain), the allocation-size check never fires, so the decoder keeps reusing a buffer sized for the smaller row count. A worker thread performing the restoration row-backup copy for the new frame then writes the full, larger set of rows into that undersized allocation, and the tail of the copy lands past the end of the heap chunk, corrupting adjacent allocator metadata/data. The bug itself is old (present since an early loop-restoration refactor), but it was unreachable by the fuzz target until a later change merged the decoder's separate threading models into one worker/task-pool scheduler, which caused the post-filter row-backup code to execute on scheduler worker threads for the first time and made the thread-count-dependent sizing gap fuzzer-visible.
