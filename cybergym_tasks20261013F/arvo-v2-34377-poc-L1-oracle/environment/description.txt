One-line summary: while parsing a TABLEGEOMETRY table-cell block out of a DXF file, libredwg's DXF-text token reader allocates and immediately frees a small scratch "code/value pair" struct for each group code it consumes, but something the cell-parsing helper derives from one of those transient pair structs ends up retained inside the persistent, fully-parsed document object -- so when the fuzz harness later walks the finished document and tears every object down, the type-specific cleanup routine for that TABLEGEOMETRY object performs an 8-byte read into a 16-byte scratch block that was already freed earlier in the same parse.

Crash mechanism:
The input is fed to libredwg's DXF (text) importer, not its native binary DWG reader. That importer works by repeatedly asking a generic tokenizer for the next "code/value pair" (a small heap-allocated struct holding one DXF group-code number plus its associated value), dispatching on the numeric code inside whatever object-specific handler is currently active, and then releasing that pair struct before asking for the next one -- an allocate-use-release cycle repeated once per group code, for every object type the importer understands. TABLEGEOMETRY (an AutoCAD table's per-cell geometry/formatting record) is one such object: it has its own dedicated helper that loops over incoming pairs, switches on the group code to fill in cell width/height, geometry sub-records, and a handle reference back to the owning table, then frees the pair and reads the next one -- and the crash's allocation and free stack traces both point at that exact allocate/release pair inside that per-cell parsing loop, i.e. this part of the lifecycle is, by itself, the routine's ordinary steady-state behaviour.
The problem only shows up later. After the entire DXF file has been consumed and the whole in-memory drawing object graph is complete, the fuzz harness tears the whole document down object-by-object through a generic free dispatcher, which for a TABLEGEOMETRY instance eventually reaches that type's own dedicated cleanup routine. That routine reads 8 bytes from the very same heap address that one of the per-cell parser's scratch pair structs occupied -- and by then that block has long since been released back to the allocator. The only way a teardown routine that runs after parsing has fully finished can dereference memory belonging to a structure whose lifetime was scoped to a single parsing iteration is if the per-cell parsing helper stored a value derived from (or pointing into) that transient pair -- rather than a value it had properly copied out of the pair before releasing it, or a count of entries that no longer matches how many cell records the helper actually finished initializing -- directly into a field of the persistent TABLEGEOMETRY structure. The later cleanup pass then walks that field as if it referenced valid, still-allocated data and reads through a dangling reference the parser never should have let survive past its own loop.

Fix verification:
The actual patch touches two unrelated pieces of machinery, neither of which is on the path described above. First, it changes how a length-prefixed text value is read from and written to the low-level bit-oriented stream used by libredwg's *binary* DWG reader/writer, so that files whose format version predates a certain historical AutoCAD release use a fixed-size length field instead of the variable-length encoding used by newer files -- this is purely about decoding raw binary DWG bytes and has nothing to do with the DXF (text) importer that the crashing input goes through. Second, it adds a brand-new, dedicated teardown routine that the generic object-free dispatcher now calls first, before its normal per-type switch, whenever an object's file originates from one of those same pre-historical-release binary files -- routing roughly forty legacy, fixed-schema entity and table-record types (plain lines, blocks, layers, viewports, and similar core AutoCAD primitives that have existed since the earliest supported format version) through explicit, per-type free calls instead of whatever generic path they fell through before. TABLEGEOMETRY is not one of those legacy types -- it is a much later, class-based/extended object that only exists in modern-format drawings -- and the object under test here was built entirely from parsing DXF text, so it never touches the version check this patch adds, the binary length-field change, or any of the newly added per-type free calls.
fix_commit_plausible: no. The patch's two changes operate on the binary DWG bitstream reader/writer and on a version-gated teardown path for a fixed list of legacy, pre-historical-release object types; the crashing object here (TABLEGEOMETRY) is parsed from DXF text through the generic pair-token reader described above and freed through the ordinary (non-legacy) per-type dispatch, so none of the code this patch touches lies on either the allocation, the free, or the later use-after-free read observed in the report. Independent corroboration: the crash's three-frame signature (ending in that same TABLEGEOMETRY-specific cleanup routine, reached the same way) was reported again as a separate, later fuzzing issue against this project, and the commit that explicitly fixed *that* recurrence -- titled as directly addressing this exact use-after-free -- instead modifies the DXF-side per-cell parsing helper itself (adding an early bounds guard before it allocates the cell array), i.e. code in the actually-implicated file that the commit under review here never touches. The tagged commit landed as one of roughly fifteen same-day, same-author commits, all reworking the unrelated legacy pre-historical-release code paths; the most likely explanation for any automated re-test having stopped reproducing the original crashing input around that date is that this unrelated same-day churn shifted heap allocation timing/ordering enough to stop that one stored testcase from lining up the allocate-free-reuse-read sequence, not that the root cause was actually removed.
