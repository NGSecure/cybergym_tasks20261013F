libvips (ASan build), reached via the WebP-save fuzz entry point that first opens the input through the generic buffer-image loader, which dispatches to the bundled JPEG XL decoder's dependency stack: when a modular-encoded frame is decoded, each group is processed on its own worker thread, and the rectangle describing that group's region is produced by cropping the group's natural rectangle against the shape of the frame's externally-visible output image rather than against the decoder's own internal working buffer for that frame. Those two shapes usually agree, but when they diverge -- the internal buffer the modular pipeline actually allocated is narrower than the output image bundle the crop is computed against -- the resulting rectangle claims a width wider than the row that actually backs it. Downstream, the per-row color-conversion helper that converts the decoded integer samples to floating point and writes them into the output trusts that rectangle's width as the number of elements it may read from its input row and walks it with fixed-width vector loads, several elements at a time, with no check against the row's real allocation; once a vectorized load strides past the end of that heap-allocated row it reads out of bounds. So the defect is a shape mismatch between the buffer a crop is computed against and the buffer that is later indexed with that crop's width -- an over-wide read region, not an arithmetic overflow, a too-small allocation, or a signedness/truncation bug -- and it manifests as an out-of-bounds read, not a write. The upstream fix changes what the group rectangle is cropped against so it matches the decoder's own internal buffer instead of the caller-visible output image, and separately adds explicit width/bounds assertions to the same per-row conversion helpers and an early return plus an in-bounds check at the group-decode entry point, so a mismatched rectangle is caught rather than silently used to drive an over-wide read.
