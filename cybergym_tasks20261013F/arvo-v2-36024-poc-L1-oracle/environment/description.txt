SleuthKit's APFS filesystem parser, exercised through the fls APFS fuzz target, ASan build: listing a volume's files walks the filesystem's catalog B-tree to resolve an object id to the metadata describing that file. The B-tree-node iterator specialized for this catalog tree materializes a slot's key and value the same way the pool's other B-tree iterator does: it derives a value pointer by subtracting an on-disk value-offset field from the node's value-table base pointer, with no check that the result still falls inside the node's own backing storage buffer, and then dereferences that pointer to read an 8-byte object id needed for the next lookup step. Because the offset comes straight from attacker-controlled on-disk node content, a crafted container image can make it large enough to walk the pointer backward past the start of the node's heap buffer and into unrelated memory. In this path, the address the pointer lands on happens to belong to a block of memory that had already been released moments earlier, during an internal reset of pool/superblock state that occurs while the pool is still being constructed -- so dereferencing that pointer to pull out the object id reads already-freed memory rather than merely out-of-range memory. The underlying defect is the same one affecting the pool's own B-tree slot-materialization step -- an on-disk offset is used to form a pointer with no bounds check before that pointer is dereferenced -- here surfacing as a use-after-free read instead of a plain out-of-bounds read because of what the heap allocator happened to place at the out-of-bounds address.
