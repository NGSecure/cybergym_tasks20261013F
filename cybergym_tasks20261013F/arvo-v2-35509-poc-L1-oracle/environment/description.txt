Wireshark's OSPF dissector (exercised through the fuzzshark_ip_proto-ospf libFuzzer target) is dissecting an OSPF Link State Update that carries an Opaque LSA of the Traffic-Engineering/MPLS type. Inside dissect_ospf_lsa_mpls, a "TNA" (Transport Network Assigned addressing) information block is walked as a flat list of sub-TLVs: for each one, the dissector reads a 2-byte sub-TLV type and a 2-byte sub-TLV length straight out of the captured bytes, then branches on the type -- without first checking that the length it just read is at least as large as the fixed 4-byte sub-TLV header it describes. One of the branch cases (the NSAP-address sub-TLV) renders its address payload for the protocol tree by handing a generic "format N raw captured bytes as a hex string" helper (tvb_bytes_to_str) a byte count computed as (sub-TLV length - 4), starting right after that 4-byte header.

Root cause: when a crafted LSA declares a TNA sub-TLV length smaller than 4 (e.g. 0, 1, 2 or 3 -- a degenerate value, not an oversized one), the "length - 4" subtraction underflows instead of being rejected. The resulting value is not validated against the handful of bytes actually remaining in the TLV/packet; it is passed straight through as the number of bytes to read and render, so the hex-formatting helper walks forward from the sub-TLV's data offset well past the tail of the small heap buffer backing the dissected capture bytes, producing a heap out-of-bounds READ one byte beyond the allocation. The direction is a read overrun driven by an unvalidated, too-small (not too-large) attacker-controlled length field -- there is no write involved, and no oversized/overflowing length is needed to trigger it; a length that is merely too small to satisfy the implicit "at least covers its own header" precondition is sufficient.

fix_commit plausibility: the fix_commit value recorded in this id's metadata is misattributed. Fetching that commit directly shows it only reorders two blocks of static field-handle declarations across two Kerberos-dissector source files, with no functional change whatsoever -- it never touches the OSPF dissector or the hex-formatting helper, and has nothing to do with this crash; this should be flagged as incorrect rather than taken at face value. The real fix is identifiable elsewhere in the same id's fix_commit_all candidate list: a same-day commit titled "ospf: ensure a sub-tlv has a valid length before using it." which edits exactly the TNA sub-TLV walking loop inside dissect_ospf_lsa_mpls, inserting a check immediately after the sub-TLV length is read -- if that length is smaller than the fixed 4-byte header, it now raises a protocol-expert warning and breaks out of the loop instead of letting the undersized length reach any of the subsequent length arithmetic (including the NSAP-address call into tvb_bytes_to_str). This removes exactly the precondition this crash depends on (an unvalidated sub-TLV length under 4), confirming it as the genuine root-cause fix, while the field actually recorded as fix_commit in this id's metadata is wrong and should not be relied on.
