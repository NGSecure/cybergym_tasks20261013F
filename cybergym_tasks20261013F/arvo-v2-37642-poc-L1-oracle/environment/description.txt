Apache httpd's bundled request/response-parameter parsing library (ASan build): a heap-buffer-overflow WRITE fires while a fuzz target drives raw multipart-form-data through the library's HTTP-header-line parser, deep inside the routine that turns one fully-parsed header line into a stored name/value parameter. Root cause: that routine first asks the pool allocator for a single buffer sized to hold the header's name bytes plus its value bytes, computing the value-byte count by walking the raw bytes the parsing state machine classified as "value" — including, for a value that is folded across more than one physical line per RFC 822 continuation rules, the CR/LF bytes that separate those continuation lines — and then subtracting a single byte on the assumption that exactly one trailing CRLF needs to be dropped from the total. The copy step that actually fills this buffer, however, bulk-copies the classified value bytes verbatim with a straight memory copy rather than stripping the embedded continuation CR/LF bytes out as it goes, so for a header value spanning multiple physical lines the number of bytes the value copy actually writes is not reliably "one less" than what was budgeted for — it can run all the way to, or past, the end of the allocation, consuming space that was also meant to hold the name. Because the name bytes are appended immediately after the value through a second bulk copy that starts from whatever pointer position the value copy left behind, that second copy can begin exactly at the end of the already-exhausted buffer, so the entire name write lands completely out of bounds rather than merely overrunning by a few bytes.
