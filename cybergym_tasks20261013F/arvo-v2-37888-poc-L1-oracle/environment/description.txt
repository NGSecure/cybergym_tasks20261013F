Apache Arrow's C++ IPC reader can be asked to re-encode the byte order of a deserialized record batch's column buffers when the producing host's endianness differs from the consuming host's. For a nanosecond-resolution calendar-interval column, the per-element byte-swap loop derives how many elements to process from the array's declared logical length as carried in the record batch metadata, instead of clamping that count to how many elements the column's actual value buffer was allocated to hold. A crafted Arrow IPC file that advertises a length value larger than the real size of its backing buffer therefore drives the loop past the end of that buffer, and UndefinedBehaviorSanitizer reports a SEGV on a read access while the loop dereferences memory beyond the allocation. This is a pure read-size/capacity mismatch, not an integer overflow or a degenerate zero/negative length sneaking past a check: the attacker-controlled length is simply too large relative to the physical buffer, so legitimate-looking loop indices walk off the end of valid memory and the stale/out-of-range pointer arithmetic is what actually faults.
