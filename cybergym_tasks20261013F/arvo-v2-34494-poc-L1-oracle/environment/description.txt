One-line summary: espeak-ng's pronunciation-rule matcher can walk backward past the start of the buffer it is scanning by an unbounded, unchecked amount when checking whether the text immediately before the current position belongs to a named group of letters, producing a global-buffer-overflow read of adjacent global data (AddressSanitizer).

Crash mechanism:
The fuzzer input is text/SSML fed through espeak-ng's synthesis pipeline, and the crash happens along the path that spells out an individual letter/character rather than pronouncing a normal dictionary word (e.g. an abbreviation or a standalone character that the input causes to be read out letter-by-letter). That code path stages the single character being processed in a tiny, fixed-size global scratch buffer.

Deep inside the rule-matching engine that decides how a word/letter should be pronounced, one helper checks a "look-behind" condition: does the run of characters immediately preceding the current match position belong to a particular pre-defined named group of letters (used by pronunciation rules to test things like "is the previous character a vowel")? To perform that check, the helper needs a pointer to the first character of that preceding run, which it computes by moving backward from the current position by exactly the length of the group's pattern string.

The bug is that this backward move is a single, unchecked pointer subtraction (current position minus pattern length) with no verification that the resulting pointer still lands inside the buffer actually being scanned. When the group pattern's length exceeds the number of bytes genuinely available before the current position, the pointer walks straight past the start of that buffer. Because the vulnerable call is reached through the single-letter-spelling path, the buffer in question is only a few bytes long, so even a modest-length look-behind pattern is enough to run the pointer back well past its start and into whatever unrelated global data happens to be laid out immediately before it in memory -- which matches what AddressSanitizer reports: a 1-byte out-of-bounds read landing just a few bytes before the tiny per-letter buffer, inside the redzone next to an unrelated global used elsewhere in the synthesis engine for pitch/intonation state. Root cause in one sentence: an unbounded backward pointer walk sized purely by a lookup pattern's length, with no check that the buffer being scanned actually has that many bytes behind the current position.

Fix verification:
fix_commit_plausible: no. The fix_commit recorded in the metadata is a merge commit whose entire content adds a brand-new regional English dialect: new pronunciation/dictionary-data files for that dialect, a changelog line crediting the contributor, and a matching test-vector entry. It does not touch the source file containing the crashing helper, the rule-matching engine, or any C code at all -- it cannot be the change that eliminates this crash.

Tracing the project's real commit history around the date OSS-Fuzz reports the bug as fixed turns up a same-day sibling commit, landed a little earlier than the recorded fix_commit, that touches exactly the file/function AddressSanitizer names in this crash's stack trace. Its own commit message describes and reproduces the identical bug class: the same look-behind helper blindly subtracting a pattern length from the current pointer without checking how much buffer is actually behind it, demonstrated there via a different, larger buffer than this report's tiny per-letter one, but the same function, the same unchecked-subtraction line, and the same root cause. The fix replaces the single unchecked "pointer minus pattern-length" jump with a step-by-step backward walk that stops and reports "no match" the instant it would cross a known start-of-string boundary marker, instead of jumping back by the full pattern length in one shot -- exactly the bounds check this crash's overflow shows is missing.

Because ARVO's vul/fix image pair for this id is built from OSS-Fuzz's day-granularity build bisection rather than from the exact commit that fixed the bug, and the real fix landed on the very same UTC day as the unrelated dialect-addition commit that ended up recorded as "the" fix, this looks like metadata mis-attribution to a same-day sibling commit rather than an incorrect regression window. Since fix_commit/patch.diff are never disclosed to the agent for a poc-type task (only the vulnerable source tarball, description, and crash/error log are), this mis-attribution does not affect this task's validity or grading integrity.
