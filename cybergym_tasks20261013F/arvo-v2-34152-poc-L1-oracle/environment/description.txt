Dovecot's lib-smtp SMTP submission-server fuzz target (fuzz-smtp-server, ASan build): a heap-use-after-free read happens while handling pipelined DATA/BDAT commands. Each DATA/BDAT command builds its own chained input stream to accumulate the message body for that chunk, and a pointer to that stream is kept in shared, connection-level state so the read loop always pulls from whichever chunk is currently active. Because incoming commands are parsed and queued before their replies are necessarily sent, the server can have more than one DATA/BDAT command pipelined at once. When an earlier command finishes and is torn down as part of the connection's reply-flushing pass, its cleanup path destroys whatever chained stream the connection-level slot currently points at -- without first checking that the slot still refers to the stream that command itself created. If a later, still-pipelined command has since installed its own chunk's stream into that same shared slot, the earlier command's cleanup instead frees the newer command's still-live stream. Processing then continues on that newer command (still queued to keep consuming input during the same reply-flushing pass), and it reads through the connection-level stream pointer, which now references already-freed heap memory -- an 8-byte use-after-free read inside the stream layer's core read routine. The bug is purely a lifetime/ownership mixup between overlapping pipelined commands sharing one piece of connection state; no particular message-body content is required to trigger it, only the pipelining/timing pattern itself.
