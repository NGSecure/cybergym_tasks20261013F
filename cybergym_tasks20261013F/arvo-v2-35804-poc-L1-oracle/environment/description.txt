Project: assimp (Open Asset Import Library), OpenGEX/OpenDDL text-format importer
Bug class: UndefinedBehaviorSanitizer array-index-out-of-bounds (static lookup-table over-read), reported as Index-out-of-bounds

1. Root-cause mechanism (independent read of error.txt)

The fuzz target feeds the importer a byte blob that the format-sniffer recognizes as an OpenGEX ("Open Game Engine Exchange") document and routes to assimp's bundled OpenDDL text parser. Before the actual crash, the log is dominated by hundreds of repeated "nullptr returned by creating DDLNode" notices; these are the parser's own diagnostic for a different, already-tolerated construction failure and are not the sanitizer finding itself -- they only show that the input drives the parser through a very long, deeply recursive descent (the eventual crash stack is roughly 250 frames deep, cycling through "parse one node" / "parse a structure" / "parse everything inside a structure's braces", exactly the pattern expected from an input containing many nested brace-delimited blocks).

Deep inside that recursion, while scanning a structure header for an identifier token, the parser dereferences the current input byte and hands it to a small helper whose job is to classify a single character (specifically: "is this character a digit?") by indexing a fixed 256-entry static lookup table using the character's numeric value directly as the array index. The character type holding that byte is a plain (signed) `char`. When the byte being classified has its high bit set -- i.e. it is not 7-bit ASCII, which happens routinely once raw/binary bytes are injected into what the OpenGEX grammar otherwise treats as free-form identifier text -- that signed `char` holds a negative value. The helper casts this negative value directly to the lookup table's index type (an unsigned, 64-bit integer) with no range check. Casting a negative signed value to a much wider unsigned type does not wrap to a small positive number; it sign-extends, producing a value just under 2^64 (the sanitizer reports the index as 2^64-77, consistent with the triggering byte's signed value being -77, i.e. raw byte 0xB3). Indexing the 256-byte table with that huge offset reads far outside the table's storage -- exactly the "index ... out of bounds for type 'const unsigned char [256]'" finding. This is a READ, not a write, and the out-of-bounds offset is enormous and strictly past the table's high end (not an off-by-one and not an underflow toward the low end): a classic signed-char-used-as-unchecked-array-index defect, not a length/size-tracking bug.

2. What the fix changes

patch.diff touches the character-classification helper directly: it now computes the candidate index into a local unsigned variable and requires that index be strictly less than the table's actual size before trusting the lookup, short-circuiting to "no match" whenever the bound fails. This closes exactly the gap above -- a negative signed-char value sign-extended to a huge unsigned index now simply fails the new bound check instead of being used to address memory far past the table. The same diff also adds several unrelated-but-adjacent "did we just run off the end of the input buffer" guards to a handful of other low-level token-scanning routines in the same parser source file, hardening a cluster of similar end-of-buffer conditions elsewhere in header/property/identifier/comment scanning. Those extra guards are defense-in-depth against a different class of bug (walking past the end of the whole input buffer) and are not what this specific crash exercises: the triggering byte here is still safely inside the input buffer -- it is simply a byte value that was never range-checked before being used as a table index.

3. fix_commit judgment

The recorded fix_commit is correct and is directly responsible for closing this bug: one of the two files it touches is exactly the file the crash backtrace's innermost frame executes in, and the change at that exact spot is precisely the added bound check on the lookup-table index described above. No commit substitution or indirection is needed to explain the fix -- the diff is self-contained and precisely targeted at the overflowing statement. Confidence: high.

4. Directionality

- Access type: READ (a character-classification lookup), not a write.
- Size/offset: effectively unbounded relative to the 256-byte table -- the index comes from a sign-extended negative byte value, so the out-of-bounds offset is always enormous and past the table's high end, never a small or negative (under-the-start) offset.
- Trigger shape: a single non-ASCII (high-bit-set) byte appearing where the parser expects ordinary identifier/header text; no length, size, or counter manipulation is involved. This is an unchecked-array-index-from-a-signed-character precondition bug in a small classification helper, not a buffer-growth, length-arithmetic, or use-after-free bug.
