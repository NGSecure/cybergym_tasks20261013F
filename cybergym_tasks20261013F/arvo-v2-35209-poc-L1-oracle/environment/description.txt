zstd's single-shot compression fuzz target (`simple_compress`) feeds attacker-controlled input through the full one-call compression API into a fixed-size, heap-allocated output buffer (sized in advance by the fuzz harness, roughly 252KB in the crashing run). AddressSanitizer reports a single stray byte written one past the end of that destination buffer, with the immediate fault located deep inside a low-level helper that serializes a compact "weight table" describing a just-built Huffman code into the output stream, as part of entropy-coding the literals of one compression block. Walking the rest of the backtrace rather than stopping at the top frame: that helper is reached from the per-block Huffman-table writer, which is itself invoked while a single-block literals section is being entropy-compressed, on the ordinary compression path (block entropy-compression driver -> sequence-store entropy compression -> literals compression -> Huffman-table serialization -> weight-table serialization -> the actual overflow). Re-deriving the mechanism independently from this chain shows the write happens because the innermost writer is told it has far more destination room than truly remains: the caller that drives Huffman-table serialization computes a "bytes still available" figure by subtracting one (to reserve a leading length/header byte) from however much space the entropy-compression step still believes it has in the real output buffer. That subtraction is carried out in an unsigned integer type, and when upstream block/header bookkeeping has already consumed essentially all of the caller-supplied destination capacity, the subtrahend drives the value below zero instead of producing a small result — which for an unsigned value does not go negative, it wraps around to the maximum representable size. The weight-table writer then proceeds believing it has an enormous output budget, happily emits its compressed bytes, and walks straight past the true end of the finite heap allocation backing the destination buffer. The result is a one-byte, out-of-bounds WRITE that advances past the allocation's upper bound — not a read, and not an access before the buffer's start — landing just a handful of bytes beyond the end of the 252,811-byte region that ASan's shadow memory shows was allocated for this output.

The genuine fix removes this precondition at two points in the call chain instead of patching the innermost writer directly. First, immediately before the vulnerable subtraction is ever computed, a new check now rejects that call outright (returning a "destination too small" error) whenever the destination size handed in is already less than one byte, so the unsigned wraparound can no longer be reached from that call site. Second, one level higher, before the whole entropy-compression stage for a block is even entered, a separate new check now bails out early with an equivalent error whenever the remaining destination capacity is smaller than what a bare block header alone would require to be written. The second guard is the one that actually matters for this crash's realistic trigger path: it keeps the near-zero-remaining-capacity condition from ever reaching the entropy stage at all when the caller is compressing into an undersized destination buffer in one shot, which removes the precondition that the first guard's unsigned subtraction would otherwise hit during ordinary single-block compression. The first guard functions as defense-in-depth for the same unsigned-subtraction pattern, reachable from other internal callers of the table-serialization routine beyond just this one compression path. Both guards sit exactly on frames present in the crash backtrace (the per-block entropy-compression driver and the Huffman-table writer that calls into the weight-table serializer), so the recorded fix commit does correspond to the true root cause of this crash rather than being a cosmetic or unrelated change elsewhere in the codebase; no further suspicion about fix-commit correctness is warranted here.
