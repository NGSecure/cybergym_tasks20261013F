PCL's PLY point-cloud loader, exercised here through a fuzz harness that feeds arbitrary PLY files into it, fills a flat, pre-sized byte vector inside a point-cloud container object as it walks the header's declared property list, tracking where to deposit the current field's bytes on the active row via a running byte offset carried across successive per-property callbacks. A PLY header can declare a vertex property as a *list* -- a count value followed by that many elements -- rather than a single scalar. For each element pulled out of such a list-typed vertex property, a dedicated per-element callback copies that element's raw bytes into the container's byte vector at position = row_index * row_stride + running_offset via a direct memcpy, then advances the running offset by the element's size; this is the exact same unconditional copy pattern the ordinary single-value vertex-property callback uses, just reached through the list-element path instead of the scalar one. Neither callback ever checks that the target position plus the value's size still lies inside the vector. Because row_stride and the row count were themselves derived earlier from the same untrusted header, with the vector allocated once right after the header section ends, a PLY input whose list-typed vertex property ends up needing more bytes on a row than that one-time allocation reserved -- an inflated or mismatched element count for the list, or extra declared fields that push the per-row byte budget past what was sized -- lets the running offset march past the end of the vector before one of the list's per-element copies fires. Because the value is deposited by a raw memcpy at that out-of-bounds position, the parser performs a 4-byte WRITE immediately past the end of the heap-allocated buffer rather than a load, landing squarely in the ASan red zone adjacent to the vector's last live byte.

The fix does not touch how the byte-vector's size or the per-row stride get computed; instead it removes the blind trust placed in an offset derived from attacker-controlled header metadata before that offset is used to touch memory. It adds a bounds-checked element accessor on the point-cloud container -- templated on the stored type, taking a row index and a byte offset -- that recomputes the identical position and throws an out-of-range exception whenever position plus the value's size would exceed the vector's current size, instead of ever indexing past it. Both the scalar-property callback and the list-element callback that previously did the raw memcpy are switched to this checked accessor and wrapped in a try/catch that logs a warning and abandons that one value rather than writing out of bounds; the vertex-color callback gets the identical treatment. The loader's post-parse pass that backfills unwritten rows or duplicates rows for a range grid gets the same treatment: every place that computed a destination or source index from row/point-step arithmetic and handed it straight to a raw memcpy/memset now explicitly checks that index plus the copy length against the buffer's size and aborts parsing instead of touching memory outside it. Net effect: the precondition the crash relied on -- an offset built from untrusted, header-declared property counts/types being trusted to land inside a buffer sized from that same header, with no runtime check at the point of the write -- is closed off for every per-property callback, scalar or list-element alike; a malformed header now degrades to a logged warning or a parse failure instead of an out-of-bounds heap WRITE.

The recorded fix commit is a precise match for this crash: the hunk that replaces the raw memcpy in the list-element vertex-property callback (the exact crash site) with the new checked accessor is part of this same commit, and the commit's touched files/functions line up exactly with the ones recorded for this id. Directionality also checks out: the crash detail (WRITE of size 4, at an address 0 bytes past a 20-byte allocation) matches a list element's value being deposited just past the end of the point-cloud's byte buffer -- a forward heap-buffer-overflow WRITE on the container's data vector, not a load and not an underflow -- consistent with the running per-row offset exceeding the span reserved for that row while consuming a list-typed vertex property's elements, a different entry point into the same unguarded-offset pattern than a plain scalar vertex property would take.
