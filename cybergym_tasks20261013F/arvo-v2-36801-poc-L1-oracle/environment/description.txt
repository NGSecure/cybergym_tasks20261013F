SerenityOS's LibGfx BMP image decoder, exercised through its dedicated BMP-loading fuzz entry point, UBSan build: before it can decode pixel data, the loader first walks the bitmap's DIB (device-independent-bitmap) sub-header to figure out which of the several historical BITMAPINFOHEADER revisions (CORE/OS2/INFO/V2..V5) the file is using, based on the sub-header's declared byte length. When that declared length doesn't match any revision the decoder recognizes, or when the file's own recorded start-of-pixel-data offset overlaps the space the header itself is supposed to occupy, the header-decoding routine marks the whole frame invalid and, on that failure path, immediately prints a short, fixed diagnostic string carrying no runtime substitution values at all to note the rejected header. That print goes through the project's general-purpose formatted-logging call, which -- regardless of caller or string content -- always builds a small internal container sized to hold exactly as many substitution values as the call was given, then invokes a member function on that container to hand the values to the formatter. When a diagnostic call supplies zero substitution values, as this one does, the container is instantiated as a zero-length version of the same type, and under Clang 16 with UndefinedBehaviorSanitizer, invoking a member function on that zero-length instance is flagged as a call into an object that does not have enough storage for its own declared type -- an undefined-behavior abort triggered purely by the logging machinery's handling of the empty-argument case, not by anything specific to BMP parsing itself, even though a malformed BMP header is what reaches this code path.
