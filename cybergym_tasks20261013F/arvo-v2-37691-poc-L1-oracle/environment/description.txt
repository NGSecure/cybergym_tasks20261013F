njs (the embeddable JavaScript engine used by NGINX's njs module), exercised through the script-processing fuzz entry point, ASan build: crashes while executing a regular-expression match whose pattern defines a large number of named capture groups (e.g. via String.prototype.match()). After running the actual regex match, the engine builds a result array sized to the pattern's total capture count and fills it with the matched substrings, then walks the pattern's compiled named-group table so each group's name can be attached as a property on the result object; for every named group it looks up which numbered capture that name corresponds to and uses that number as the index into the just-built result array to fetch the value to attach. That per-group capture number is reconstructed from two raw bytes stored in the compiled pattern's name-table metadata by shifting one byte and adding the other, with the bytes read through a plain (signed) character type instead of an unsigned one; once a pattern has enough named groups that a capture number's encoded byte has its high bit set, the signed interpretation sign-extends that byte to a negative value, so the "reconstructed" capture number comes out wildly wrong (often negative) rather than being a legitimate position inside the result array. That bogus number is then used directly as an array offset with no range check against the array's real size, producing a pointer far outside the array's actual allocation. The property-construction helper that is handed this wild pointer simply copies the 16-byte value it points to into the new property slot — a READ dereference of that pointer — and because the computed address lands completely outside any mapped/ASan-shadowed region (not merely one or two elements past the end), the process takes a raw SIGSEGV instead of a normal bounds-checked heap-buffer-overflow report.
