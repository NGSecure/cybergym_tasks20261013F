net-snmp's client-side PDU-construction library, exercised through its API fuzzing entry point (ASan build): when a caller adds a variable binding whose syntax type is the bit-string enumeration type, the library takes a human-readable value -- a list of individual bit-position tokens, each either a raw number or a symbolic label resolved against the loaded MIB -- and encodes it into a wire-format byte string one token at a time. For each token it computes which byte of the output buffer that bit position falls into, and if that byte index looks too large for the buffer's current size it performs a single buffer-growth step before falling straight through to a read-modify-write bitwise-OR that sets the bit in that byte. The growth step does not derive the new buffer size from the specific index that triggered it; it just grows the allocation by some fixed strategy and then trusts that to be sufficient, without re-checking the index against the buffer's actual new length afterward. When a single bit-position token is large enough that its byte index still lands beyond the just-grown allocation -- or the token's value gets mishandled during the text-to-integer-to-index conversion -- the subsequent bitwise-OR touches memory outside the heap allocation. AddressSanitizer flags this as a small out-of-bounds read because the compound assignment reads the target byte before writing it back; the faulting access occurs a single call deep from the fuzz harness's one entry point, inside the same client-side encoding routine that had just performed the undersized growth. The root defect is a missing bounds check: nothing validates, after the growth attempt, that the computed byte index is still within the buffer's bounds (in either direction) before the code commits to touching that index.
