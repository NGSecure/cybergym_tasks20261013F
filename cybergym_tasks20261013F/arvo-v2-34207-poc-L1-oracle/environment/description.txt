Summary: A malformed MQTT SUBSCRIBE acknowledgement (SUBACK), received in reply to a subscribe request, triggers a SEGV caused by a WRITE to a wild address in the client's MQTT property-list cleanup routine while the received packet is being decoded (this is a 32-bit AddressSanitizer build; the faulting write is to 0xf4f400ee).

Root cause: When decoding a SUBACK, the client treats the packet's remaining payload as the list of per-topic return/reason codes and, in the vulnerable build, accepts that list without any bound on how many codes it contains -- it simply aliases the return-code list as a raw pointer into the receive buffer and consumes as many codes as the packet's declared remaining length claims, never clamping to the client's small fixed capacity of 12 entries. A SUBACK whose remaining length implies far more return codes than the fixed-size acknowledgement/topic storage can hold drives an out-of-bounds access during decode; the observable consequence is that the decoded MQTT-property-list pointer held in the acknowledgement object is corrupted, so when the decode path then frees that property list it walks and writes through the corrupted pointer, dereferencing an unmapped/wild address and crashing with a SEGV WRITE. The offending quantity is the SUBACK return-code count, which grows past the fixed 12-entry limit; the bad access is a write, performed while freeing the corrupted property list.

Fix note: The referenced fix commit matches this crash. It rewrites exactly the SUBACK-decode-and-populate path on the crash stack: the return-code list is changed from an unbounded raw pointer into the receive buffer (return_codes = rx_payload) to a fixed-size array of 12 (MAX_MQTT_TOPICS) with an explicit clamp (if remain_len > MAX_MQTT_TOPICS, remain_len = MAX_MQTT_TOPICS), and the client-side loop that copies return codes back to the subscribe topics is bounded to the same 12-entry limit instead of iterating over the attacker-supplied topic count. That bounding of the return-code count is precisely what prevents the out-of-bounds handling that corrupts the property-list pointer, so the fix addresses the condition observed here. The additional thread-locking changes bundled in the same commit are unrelated concurrency hardening.
