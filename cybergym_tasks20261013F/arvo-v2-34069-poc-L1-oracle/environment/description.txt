One-sentence summary: A crafted/corrupted HFS+ image drives the filesystem module's directory-listing / path-resolution logic into a heap-buffer-overflow read when it uses a disk-supplied, unvalidated key-length field to compute a byte offset into a small, freshly-read catalog B-tree node buffer.

Crash mechanism:
- The fuzz target opens an HFS+ volume image and asks the library to resolve a path to an inode number, which internally walks a directory's catalog children one path component at a time to find the matching entry.
- That directory listing is implemented by having the catalog B-tree walk invoke a per-record callback for every record it visits in a leaf node, so the callback can check whether the record belongs to the folder being listed and, if so, pull out its type and metadata.
- Records inside a leaf node are packed back-to-back: a length-prefixed key first, then immediately after it the record's actual payload (a 16-bit type tag, followed by type-specific fields). The callback computes where the payload begins by reading a 16-bit "key length" field straight out of the key and adding a small fixed offset, then indexes directly into the node's raw byte buffer at that computed position to read the payload's type tag.
- That key-length field comes straight from the volume image and, at the point it is used as an index, is not checked against how many bytes the node buffer actually holds for this call (137 bytes in this crash). A crafted image can make one record's key claim a length large enough that the computed payload offset lands at or past the very end of the node's allocation.
- When that happens, the read of the two-byte type tag at the computed offset falls (at least partially) outside the heap allocation; AddressSanitizer flags the very first out-of-bounds byte of that read as a 1-byte heap-buffer-overflow.
- The recorded fix commit addresses this together with a related but structurally distinct bug reached through a different call path in the same catalog-traversal machinery (compared via the embedded-name/Unicode-string route rather than this record-offset route). The common thread across both is that the low-level per-record callback interface shared by this catalog code did not carry along how many bytes of key data / how large the node buffer actually was, so more than one call site independently trusted a disk-controlled length field when computing an offset or index into that buffer.

Trigger conditions (mechanism-level, not byte-exact): an HFS+ catalog B-tree leaf node containing a record whose length-prefixed key declares a key length large enough that "key length + fixed header size" computed from it points at or beyond the end of the node buffer actually read from the image, encountered while the library is resolving a path (walking a directory's children looking for a specific catalog entry by name).

Fix verification: the recorded fix commit is a single, coordinated hardening pass across four files spanning exactly the areas this bug touches: the core catalog/extents traversal code, the directory-listing code, the Unicode name-comparison code, and the shared header declaring the internal per-record callback interface used by the catalog walk. The directory-record callback this crash's stack identifies is changed to receive two new explicit parameters -- the actual key length and the actual node-buffer size for the record being visited -- threaded through the shared callback typedef, which is updated to match. Two new checks are added: one rejects a key that is too short to even contain the length field before that field is trusted, and a second -- inserted immediately before the computed offset is used to index into the node buffer -- rejects any offset that would not leave room for the full type-tag read. That second check sits directly in front of, and directly guards, the exact indexing operation this crash's own stack shows overflowing.

fix_commit_plausible: yes, high confidence. The new bounds check is inserted immediately before, and guards exactly, the buffer-indexing operation performed in the function named in this crash's top stack frame, using precisely the value (the computed record offset within the node) whose lack of validation produces this crash's out-of-bounds read. The patch does not touch unrelated code paths for this crash -- every hunk in the diff is either this exact fix or one of a small number of sibling bounds checks added to other callback sites sharing the same previously-unvalidated-length pattern (including the separate bug this same commit also fixes).
