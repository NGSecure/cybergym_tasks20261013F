mruby's bytecode interpreter, when fed malformed/fuzzed Ruby source through the plain C fuzz driver, crashes with a wild-address segmentation fault on a read inside a small inline helper that fetches the captured-locals environment object attached to a call frame; the helper is invoked while the interpreter is tearing down (popping) the frame for a method call that has just returned. Root cause: the same stale-bookkeeping defect that affects this interpreter's instruction-dispatch loop elsewhere — three "extended encoding" prefix opcodes, used to let a handful of less-common instructions carry a wider operand, jump straight into shared per-opcode body code without first refreshing the active call frame's saved instruction-pointer field to the operand location they just consumed, leaving that field pointing at a stale, pre-prefix spot. When a method call made from inside one of these extension-prefixed instructions subsequently returns, the frame-teardown logic walks back up the call-info chain and, among other bookkeeping, reads each popped frame's recorded closure/environment reference to decide whether that environment needs to be unlinked from the live stack. Because the calling frame's saved instruction-pointer field was never advanced past the leftover stale value, the teardown logic ends up treating an unrelated bit pattern as though it were a legitimate environment reference, and dereferencing it walks off into unmapped memory, producing the segmentation fault.
