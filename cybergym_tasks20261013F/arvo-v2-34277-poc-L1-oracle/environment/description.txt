Summary: A type-confusion bug in DuckDB's SQL-parser AST-to-internal-representation conversion layer lets a FROM-clause "table function call" reference be built from an AST node that is not actually the function-call node kind the code assumes, leading to a wild-pointer read and SIGSEGV.

Crash mechanism: When the parser processes a table reference written as `name(...)` in a FROM clause, the internal Postgres-flavored grammar can hand back one of several different AST node kinds for the callee sub-expression, depending on exactly how the surrounding syntax is written. The vulnerable code path that turns this callee node into DuckDB's internal table-function reference only *assumed* — via a debug-only assertion that is compiled out in the release/fuzzing build used here — that the node it received was always the "plain function call" variant. It then unconditionally reinterpreted the generic AST-node pointer as that specific struct type and read one of that struct's fields (the callee's name list) straight out of the reinterpreted memory. When the fuzzer instead produces input where that FROM-clause slot is populated by a different, differently-shaped AST node kind (one that overlaps in the node-tag header but not in the rest of its layout), the "name list" field read lands on whatever bytes happen to sit at that offset in the real (smaller/different) struct — an uninitialized or otherwise bogus pointer. Dereferencing it produces the observed "dereference of a high value address" wild-address read and crashes with SIGSEGV while still inside the routine that turns a parsed function-call node into an expression, itself invoked from the code that builds a table reference out of a FROM-clause function call. No heap/stack corruption is required beforehand — this is a pure type-confusion / missing-validation bug triggered purely by the shape of the parsed query text.

Fix verification: fix_commit_plausible = yes. The fix replaces the debug-only assertion + unconditional-cast pattern in the FROM-clause function-reference-building code with an explicit check on the callee AST node's real type tag: the "plain function call" case is handled as before, a new case is added to correctly handle the other AST node kind that was previously silently mis-cast, and any other node kind now raises a normal parser error instead of being blindly reinterpreted. This directly closes the type-confusion path that produced the crash, and the call chain in the crash backtrace (parsing a FROM-clause callee down into the function-call-to-expression conversion routine) lines up exactly with the function this change modifies. The same commit also threads a new recursion-depth counter through essentially every expression-transformation routine in the parser (capped at a fixed maximum depth, throwing a parser exception past it) — this is a separate, bundled hardening against unbounded-recursion stack exhaustion in deeply nested expressions, unrelated to this crash's root cause but shipped in the same parser-hardening commit.
