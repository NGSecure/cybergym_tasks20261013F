A stack-buffer-overflow (ASan, 1-byte READ) occurs in ImageMagick's PDF coder while it is scanning a PDF file's leading metadata section (version banner, spot-color names, cross-reference-adjacent fields) ahead of the actual image decode. That scan is a simple state-machine loop built on top of a small byte-staging helper: the helper keeps a fixed-size, on-stack lookahead array plus a cursor into it, refilling the array from the underlying blob whenever the cursor reaches the end of what was last read, and reporting end-of-stream once a refill comes up empty.

Two of the scanner's sub-loops — one that copies a comment/version line into a local buffer, and one that dispatches on a "/"-prefixed field name — each correctly stop pulling further bytes the moment the helper reports end-of-stream. The outer scanning loop, however, does not check that condition before looping back for its own next byte: it unconditionally asks the helper for one more byte to decide whether to keep going, even though the inner sub-loop it just ran already observed the stream's end. The helper's "give me the next byte" entry point advances its cursor on every single call, regardless of whether a refill actually produced new data at that position — so once the true end of the input has been reached, each further call from the outer loop advances the cursor one more step with nothing re-validating that the cursor still falls inside the backing array. A PDF crafted so that one of these metadata fields (e.g. a comment/version line) runs right up to the end of the file lets the outer loop take that extra, unguarded step past end-of-stream; because the backing array is embedded directly in the enclosing function's own stack frame (not heap-allocated), walking the cursor past its bound and then indexing into the array for "the byte at the cursor" is an out-of-bounds stack read rather than a crash-free no-op. This is purely a READ-direction bug: the overflowing access fetches a byte from the on-stack lookahead array at an out-of-range offset; nothing is written out of bounds, and no attacker-supplied heap pointer is involved — the overread buffer is the parser's own internal staging storage.

The patch is a genuine, narrowly-targeted fix to this exact code path: it inserts two guard checks, placed right after each of the two inner sub-loops described above, that make the outer loop stop immediately once end-of-stream has already been seen there, instead of looping back for one more (unguarded) byte. This directly closes the call sequence that lets the cursor run past the array's bound. A companion one-line change in the byte-staging helper itself adds an explicit integer cast on the value it returns; this is a type-clarity tidy-up bundled into the same commit rather than a second behavioral fix — the underlying byte already promotes to the same integer value either way, so it does not by itself change what gets read or how far the cursor can travel. Diffing the vulnerable and fixed source trees confirms the patch touches only these two files/functions and matches the published patch exactly, with no unrelated or test-harness-only changes mixed in.
