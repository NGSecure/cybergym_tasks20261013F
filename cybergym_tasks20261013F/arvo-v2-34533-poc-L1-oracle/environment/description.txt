espeak-ng's SSML text-to-speech fuzz target (ASan build): decoding an input whose text buffer ends immediately after a short run of literal period characters -- long enough to be considered for the "three or more dots become an ellipsis" rule, but not actually reaching that threshold before input runs out -- triggers a 1-byte heap-buffer-overflow read past the end of the fuzzer-supplied input buffer.

Root cause: the clause-tokenizing text reader pulls characters one at a time from a small UTF-8 decoder that tracks a current position and an end-of-buffer boundary, and separately keeps a one-character lookahead/pushback slot so a character that turns out not to belong to the current token can be "put back" for the next read. That pushback slot uses the integer value 0 to mean "nothing is currently pushed back" -- but 0 is also exactly the value the character reader legitimately returns once the decoder's position reaches the end of the buffer (its end-of-input sentinel). When the dot-run-counting loop reads that end-of-input value while still hunting for a third dot, it decides the run isn't an ellipsis after all and tries to push the just-read value back for the caller to re-consume. Because the value being pushed back happens to be the same 0 used for "pushback slot is empty," the push-back is silently lost instead of being remembered. The very next character request therefore finds nothing waiting in the pushback slot and falls through to ask the low-level decoder for another character directly -- but the decoder's position is already sitting exactly at the end of the buffer it was handed, and this particular call path never checks for that condition before dereferencing. The decoder advances its read pointer one more byte and reads it, landing one byte past the allocated input buffer -- the reported out-of-bounds read.

fix_commit_plausible: yes. The available patch adds an explicit "not at end of buffer yet" guard in front of every character-pulling loop condition in the affected clause-reading routine, including the exact dot-run-counting loop described above, so that once the decoder's position reaches the buffer boundary no further character request is issued at all -- sidestepping the zero-value pushback/end-of-input collision rather than fixing the pushback slot's sentinel encoding directly. The crash's own call stack (decoder-level UTF-8 byte read, reached through a generic "get next decoded character" wrapper, reached from the clause reader) lines up exactly with the loop the patch modifies, and the recorded before/after differential (crashes on the vulnerable build, does not crash on the patched build) is consistent with this being the real fix rather than an unrelated change.
