Draco's point-cloud decoding path (reached through the honggfuzz point-cloud-decoding entry point, built with an address sanitizer) includes a kd-tree-based attribute decoder that supports a quantized-position-specific encoding method for reconstructing point coordinates. That method's handler assumes, without ever checking, that it is only ever asked to reconstruct a single point attribute made up of exactly three components (the ordinary x/y/z case) before it hands decoding off to the shared tree-based float-point decompression routine. That shared routine reconstructs one point's coordinates at a time into a small, fixed-capacity accumulator on the stack that is sized for exactly three components, dequantizes them, and then forwards the accumulated values through a generic per-component attribute-value copy helper that blits them into the attribute's backing storage — a helper whose copy size is driven by how many components the target attribute was actually declared to have. When the point attribute set handed to this method does not in fact match the single three-component shape the method silently assumes, the generic copy helper ends up moving more bytes out of the fixed three-component stack accumulator than it was ever sized to hold, running the read past the bounds of that stack-resident buffer. Root cause: the quantized-position decoding method never validates that the attribute configuration it is about to decode actually matches the single, three-component shape its downstream fixed-size stack accumulator silently assumes.
