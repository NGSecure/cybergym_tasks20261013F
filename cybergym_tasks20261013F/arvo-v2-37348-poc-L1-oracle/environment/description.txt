This is a heap-buffer-overflow (read of 4 bytes) reported by AddressSanitizer inside HarfBuzz's font subsetter, triggered while it rebuilds a color-palette (CPAL) table during the serialize/copy phase of subsetting. When the subsetter copies the palette's color-index entries into the new output blob, the number of 4-byte entries to copy is taken from palette and record counts declared in the font's own CPAL table header, without first checking that count against how much color-record data the supplied font actually still has backing it. A generic serialize-copy helper then walks that attacker-controlled element count straight off the source object, reading each 4-byte entry in turn; because the crash address lands exactly at the first byte past the end of the heap allocation holding the input font data, this is a tight one-element over-read rather than a wild out-of-bounds access: the declared entry count is one larger than the data actually available, so the final loop iteration reads 4 bytes beyond the buffer. The faulty pointer is on the read/source side (the font's own palette array), not a write destination, and the bug is a pure missing-bounds-check issue (an oversized/unvalidated length driving an array read) rather than a use-after-free or a degenerate value that bypasses an existing guard; any other table-subsetting path that derives a copy length from header-declared counts without cross-checking it against how much backing data is truly left would be susceptible to the same class of over-read.
