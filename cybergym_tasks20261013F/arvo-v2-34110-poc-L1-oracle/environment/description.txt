Summary: A 1-byte heap-buffer-overflow READ occurs while the CPython interpreter scans a code object's exception table to find the handler for the current bytecode offset, when a marshal-loaded code object carries a malformed/corrupted exception table.

Root cause: CPython's "zero-cost" exception handling encodes each function's exception-handling ranges as a compact table of variable-length entries, where a byte with its high bit set marks the start of a new entry and bytes with the high bit clear are continuation bytes belonging to the current entry. During exception dispatch, the interpreter must skip forward from the current position to the start of the next entry; it does this with a tight loop that simply advances a pointer one byte at a time as long as the current byte's high bit is 0, stopping only when it sees a high-bit-set byte. That loop takes no upper bound: it never compares the advancing pointer against the end of the table's backing allocation, so it only terminates because it (correctly-formed data) eventually finds a marker byte. Here the exception table backing bytes come from an untrusted marshalled object built via marshal.loads() inside the fuzz harness; the crafted table's bytes never contain the expected high-bit-set marker before the table's actual allocated end, so the skip loop reads one byte past the end of the heap-allocated buffer holding the table (an 81-byte allocation) — a 1-byte out-of-bounds READ just past the buffer, not a write, and the pointer only ever advances forward (increasing address), never backward.

fix_commit judgment: fix_commit matches the crash. The patch changes exactly the function at the crash site: it adds an explicit `end` bound parameter and rewrites the skip loop's condition from an unconditional "advance while high bit is 0" to "advance while high bit is 0 AND the pointer is still before `end`", with `end` computed from the exception table's real length and threaded in from the caller that performs the per-bytecode-offset handler lookup. This directly bounds the same pointer-advancing loop that produced the out-of-bounds read, so the fix addresses the exact condition (an unterminated/corrupted exception-table encoding with no bound check) that caused the crash.
