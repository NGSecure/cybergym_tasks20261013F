jsoncons JSON round-trip fuzzer (parse a JSON document with json_reader and immediately re-serialize it through a json_string_encoder, ASan build): while re-encoding an object key that contains several C0/DEL-range control bytes (0x00-0x1F or 0x7F), the string-escaping routine that writes the `\u00XX`-style escape for each such byte decodes it as a one-byte "codepoint" and advances its own cursor to just past that byte -- but the surrounding character-by-character loop that drives the escaping routine *also* advances its cursor by one after every iteration, regardless of whether the current byte was handled by the plain path or by the control-byte path. For every control byte encountered, the effective advance is therefore one byte too many. Because the key here contains a run of many such control bytes packed close together, the extra per-byte drift accumulates across the string and the combined cursor overtakes the true end of the key's character range without ever landing exactly on it, so the loop's "not yet at end" check never sees the cursor equal to that boundary and stays true well past it. Having skipped clean over the key's own end, the loop keeps consuming whatever bytes happen to follow as if they were still part of the key -- in this input, several more structurally significant JSON bytes (the key's own closing quote, the following colon, and further container-syntax bytes) -- each an ordinary single-byte advance, until the cursor finally runs off the end of the entire input buffer the parser handed to the encoder and reads one byte past it -- still inside the parser's underlying read-buffer allocation, but outside the region ASan considers "in use" for that buffer -- producing a 1-byte out-of-bounds container read. So the actual overrun is not immediately adjacent to the key; it is the cumulative result of the drift skipping the key boundary and then continuing through the rest of the input before finally overrunning the buffer itself. The bug is purely in how many bytes the escaping loop consumes per control character; it has nothing to do with multi-byte/non-ASCII UTF-8 decoding, JSON structural parsing, or memory allocation sizing.

fix_commit_plausible: yes. The fix rewrites exactly the escaping routine identified as the crash site: instead of reassigning the loop cursor to an absolute "one past this codepoint" pointer returned by the low-level decode call (which combined with the loop's own per-iteration increment produced the double-advance for single-byte codepoints), it now advances the cursor by `sequence-length - 1`, i.e. by zero extra bytes for a one-byte control character, deliberately leaving the loop's own increment as the sole source of advancement for that iteration. That is a direct, mechanically-correct fix for the accumulating-drift/off-by-one-per-control-byte bug described above (a companion change in the underlying codepoint-decode helpers also makes them always initialize their output codepoint before any early-return path, a related but secondary hardening in the same code area). A regression test embedding the exact crashing byte sequence (an object key consisting of a long run of control bytes) is added alongside the fix, matching the crash mechanism precisely.
