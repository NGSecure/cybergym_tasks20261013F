matio's MAT-file reader, when handed a MATLAB MAT v7.3 file (which is actually an HDF5 container under the hood), delegates the real work of opening the container to matio's bundled HDF5 library rather than parsing it itself. Early in opening any HDF5 file, the library must locate the file's root group, which requires loading the very first object header and decoding each message stored in it. Object headers are read in chunks, and the raw bytes making up a chunk are copied into a freshly allocated heap buffer whose size is taken directly from a chunk-size field recorded earlier in the same header structure — that field is trusted completely, so the buffer is sized to exactly that many bytes, no more. One of the message types a chunk can hold is a short "continuation" message, and its decoder is written to always pull a fixed two-field layout straight out of the chunk buffer: first a file address whose byte width is fixed by the file's superblock, then a length value whose byte width is likewise fixed by the superblock, both read at hard-coded, back-to-back offsets with no check of how many bytes actually remain in the buffer before each field is consumed. If a file is crafted (or simply truncated) so that the chunk-size field for an object header claims a size a few bytes smaller than this address+length layout needs, the heap buffer that gets allocated for that chunk is correspondingly undersized, yet the continuation-message decoder still walks through both fields unconditionally, with no bounds check tying the read to the buffer's actual allocated length. The final byte(s) of the second field then fall just past the end of that heap allocation, producing a small heap out-of-bounds read triggered purely by a mismatch between an object header's declared chunk size and the fixed, unconditionally-consumed byte width of its own continuation message.
