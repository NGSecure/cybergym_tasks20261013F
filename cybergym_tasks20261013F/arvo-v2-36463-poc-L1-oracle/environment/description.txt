MuPDF's software rasterizer represents nested clip and soft-mask regions as a stack of per-level rendering states: entering a clip region pushes a new level, and the routine responsible for building an image-mask clip is expected to either populate that new level with a freshly built mask pixmap or, if it decides no actual mask region is needed, explicitly mark the level as empty (null mask, empty scissor) before returning, so that whatever later pops this level knows there is nothing to composite. One specific early-return branch of that routine -- taken when the portion of the source image that would actually need to be sampled works out to be empty -- omits that "mark as empty" step, unlike the routine's other early-return branches, which do perform it. Because a freshly pushed level starts out as a raw field-by-field duplicate of the level beneath it, the omission leaves the new level's mask field holding a copy of whatever mask pointer happened to be active one level down, rather than a null sentinel. Later, when the matching pop for this clip level is reached, the pop logic sees a non-null mask and concludes a real sub-region was built, so it proceeds into the pixel-blending routine that composites through that mask -- which ends up reading pixel data through a pointer that, by that point in the content stream's processing, no longer refers to a live pixmap, because the object it was copied from has since been released. The result is a one-byte heap-use-after-free read inside the mask-compositing code, triggered purely by the push/pop bookkeeping mismatch on that one early-return path, not by any issue in the compositing math itself.
