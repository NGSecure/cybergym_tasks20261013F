wasm3's libFuzzer harness parses and compiles a WebAssembly module's bytecode; compiling a function body dispatches on each instruction's opcode, and for the 0xFC-prefixed "extended opcode" family the compiler does a second-level lookup keyed on the byte following the 0xFC prefix, into a table that only has entries for a small, fixed set of implemented extended opcodes at low byte values. Any 0xFC-prefixed instruction whose following byte falls outside that implemented range fails the lookup, and the dispatch code immediately reads a handler-function-pointer field out of whatever the lookup returned -- without first checking that the lookup actually succeeded -- then unconditionally calls through it. Because the failed-lookup case was never validated, the value read and invoked is indeterminate rather than a safely-checked NULL, so under an optimized MSan build the resulting indirect call does not reliably fault at the dispatch site itself; instead execution runs whatever code happens to sit at that indeterminate address, and the crash that actually surfaces depends on what the wild jump lands near for a given input. In this crash the reported backtrace is internally inconsistent with wasm3's real control flow in a telling way: the two innermost frames are the module's element-segment initializer and the module-loading routine that calls it once, early, before any function body is ever compiled -- yet they appear here nested *beneath* the function-body compiler and the lazy-compile entry point that only runs afterward, once loading has already finished. That ordering cannot occur in a real, well-formed run; the most consistent explanation is that the wild indirect call corrupted the stack/frame-pointer chain enough that the crash unwinder picked up stale return-address bytes left over from the module's earlier, already-completed load step, and mis-attributed them as live frames beneath the genuinely-executing compiler frames above them. The actual fault is a read against state (module/table bookkeeping) that was never legitimately in scope at the point execution had really reached.

Fix verification: the fix commit adds exactly one missing check at the extended-opcode second-level dispatch site -- before reading and calling through the handler-function-pointer field, it now verifies the table lookup actually returned a valid entry and throws a clean "unknown opcode" compile error otherwise. The PoC's function body contains a 0xFC extended-opcode prefix immediately followed by a byte value well outside the small implemented range, i.e. exactly the malformed shape that produces the wild jump and the resulting corrupted/stale backtrace seen in this crash. With the guard in place, compilation aborts cleanly instead of taking that wild jump, so the stack never gets into the corrupted state this crash depends on. The same commit separately gates a module's start-function execution behind a fuzzing-only build flag; that change affects a different, execution-time code path this PoC never reaches (the crash happens purely during compilation, before any code from the module would run), so it plays no role in fixing this specific crash. fix_commit_plausible: yes (high confidence) -- the PoC bytes contain the precise malformed-extended-opcode pattern the guard targets, and a backtrace whose call order violates the harness's actual control flow is only explicable as corrupted state from the wild indirect call the guard prevents.
