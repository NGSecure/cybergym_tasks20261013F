wolfMQTT's MQTT v5 packet decoder (exercised through the wolfmqtt-fuzzer libFuzzer target over a client-side MqttClient_WaitMessage/DecodePacket call chain), ASan build: while walking an MQTT v5 property list attached to an AUTH packet, the decoder handles a "user property" entry -- a pair of length-prefixed strings (name then value) -- by first reading the name's 16-bit length header and immediately advancing its running cursor and its "properties bytes remaining" counter by that header size plus the attacker-controlled name length, with no check yet performed that the claimed length actually fits inside the bytes still available in the receive buffer. Only after this unconditional advance does the code attempt to validate the length it already consumed, so by the time any check runs the cursor may already sit past the true end of the buffer; a crafted name length large enough drives the cursor arbitrarily far beyond the allocation with nothing having rejected it. On the next iteration of the property-list loop, the decoder recomputes how many bytes remain by subtracting this (already past-the-end) cursor position from the total buffer length; because the cursor has overrun the buffer, that unsigned subtraction wraps around to a huge value instead of a negative one, so it looks like plenty of room is left. That bogus "remaining" value is then handed to the shared variable-byte-integer reader used to decode the next property identifier -- a routine whose own internal guard only refuses to read when the *reported* remaining-length argument is too small, which this wrap-around has defeated -- so it dereferences the wandering read cursor, which by now points far outside any valid heap object. The result is a 1-byte heap-buffer-overflow READ that AddressSanitizer flags as a "wild pointer" (far-from-bounds) access rather than a tight off-by-one at a buffer edge, because the pointer was never anchored to the real allocation in the first place. This is a trust-before-verify ordering bug -- an attacker-controlled length field is consumed and used to move a cursor forward before its legality is checked, and the one validation that does exist for it fires too late (after the advance) and on data that no longer reflects the true bounds, while a later, logically separate bounds check (in the length-field reader) is defeated only as a side effect of the earlier unsigned-wraparound corruption, not because that check itself is missing.
