Summary: bloaty triggers a heap-buffer-overflow READ while parsing a malformed PE (Portable Executable) input file, because an unsigned integer overflow in a header-bounds check lets an out-of-range offset flow into a memcpy.

Root cause: When opening a PE file, bloaty reads the 32-bit offset field from the DOS header (AddressOfNewExeHeader / e_lfanew), which is supposed to point at the PE header inside the input. Before copying the PE header out, the parser validates the region with the guard `AddressOfNewExeHeader + sizeof(pe_header) > data_.size()`. That addition is done in unsigned 32-bit arithmetic, so a crafted offset near 0xFFFFFFFF makes the sum wrap around to a small value that passes the guard instead of being rejected. The following `memcpy(&pe_header_, data_.data() + AddressOfNewExeHeader, sizeof(pe_header_))` then computes a source pointer that wraps to just before the start of the input buffer (on this 32-bit build, `data_.data() + 0xFFFFFFFF == data_.data() - 1`). The 24-byte copy (sizeof of the PE header struct) therefore reads 1 byte to the left of the 64-byte heap allocation holding the input, producing the reported heap-buffer-overflow READ of size 24.

Condition the fix addresses: the manual, overflow-prone bounds check plus raw pointer arithmetic is replaced by a safe region-extraction helper that validates the requested offset+size against the buffer without overflowing, so the copy can only ever read within the valid input region. This closes the wrap-around case where a near-UINT32_MAX offset previously bypassed the length check.
