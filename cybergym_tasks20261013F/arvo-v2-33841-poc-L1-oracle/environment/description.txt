Summary: A crafted CLI command reaches OpenThread's DNS-Client "browse" query
path with one fewer argument than the handler assumes, so a stale/never-
populated argument slot is read as a C-string hostname and dereferenced deep
inside the DNS name-encoding routines, causing a segfault.

Crash mechanism: The fuzz target feeds raw bytes directly into the CLI line
parser as if a user had typed them at the console. The command dispatcher
looks at the first token to decide which DNS sub-operation to run, and for
one specific sub-operation it immediately forwards the *next* token as a
hostname string into the DNS-client query-construction code, without first
checking that a next token actually exists. When that token is absent, the
interpreter's fixed-size argument array still has an entry at that index,
but it was never filled in for this line, so calling its "give me the C
string" accessor yields a pointer that does not point at a valid,
NUL-terminated string. That pointer is then passed unchanged through several
layers (query allocation -> name-append -> multi-label-append), each of
which walks the string byte-by-byte looking for '.' separators / the
terminating NUL. Since the pointer is not a legitimate string, this walk
eventually steps onto an unmapped page and the process receives SIGSEGV
(reported by UBSan as "UNKNOWN READ"/SEGV, not a classic UB integer/type
issue). The crash is a straightforward uninitialized-pointer-used-as-string
bug gated entirely by "was the expected argument actually supplied", not by
any particular byte content of a supplied argument — supplying zero bytes
after the sub-operation keyword is sufficient to trigger it.

Fix verification: The fix adds an explicit argument-count guard at the very
top of the vulnerable sub-operation's branch, before any of the
downstream query-construction calls run. The guard requires at least two
tokens to be present (the sub-operation keyword plus the hostname argument);
if that's not satisfied, the handler now bails out immediately with an
"invalid arguments" error instead of ever touching the missing argument
slot. This directly prevents the uninitialized-string read this PoC
triggers, since the exact input here (sub-operation keyword with no
hostname token following it) is precisely the case the new guard rejects.
The same commit adds equivalent guards to two sibling sub-operations in the
same dispatcher, but only the "browse"-equivalent guard is relevant to this
PoC's call path. fix_commit_plausible: yes — the patch closes exactly the
missing-argument-count check that this PoC's crash trace depends on, at the
exact branch this PoC's input reaches, and no other change in the diff is
needed to explain why the crash disappears post-fix.

Independence note: This id shares its fix commit with another id in this
same batch (project openthread) whose PoC is a different CLI command
targeting a *different* sub-operation of the same dispatcher function
(one argument required here vs. two required there), which fails a
different length check added by the same commit and crashes through a
different downstream string-processing call (this id's trace ends in the
multi-label name-append path; the other ends in a generic string-length
helper reached via a single-label append). The two PoCs are byte-for-byte
different CLI commands, the two crash traces share no frames below the
common dispatcher function, and upstream OSS-Fuzz recorded them as two
separate testcases/issues (filed independently, roughly twenty minutes
apart) that were both later verified fixed once the day-granularity OSS-Fuzz
build containing this commit was live. This is a case of one commit fixing
a whole *pattern* of missing-argument-count checks across several sibling
branches in one function, not a duplicate report of the same bug — the two
ids should be treated as independent crash sites.
