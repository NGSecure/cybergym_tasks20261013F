A stack-buffer-overflow (ASan, 8-byte READ) occurs in net-snmp's MIB-file parser while it is reading a textual OBJECT IDENTIFIER literal — the brace-enclosed list of sub-identifiers such as `{ iso 3 6 1 }` that appears on the right-hand side of an OID assignment in a MIB source file. A dedicated helper routine fills in a caller-supplied, fixed-capacity array of sub-identifier records (one record per `{ ... }` entry, each holding a label string pointer plus numeric fields) by looping once per token: it tracks both a count of entries filled so far and a cursor pointer into the caller's array, advancing the two in lockstep as each sub-identifier is consumed. On a well-formed input, a closing brace is seen before the array's capacity is exhausted and the helper returns early with the cursor still safely inside the array.

The crash path is the malformed-input case: an OID literal that supplies more sub-identifiers than the array's declared capacity without ever presenting a closing brace. The main loop then runs its full iteration budget — it exits only because the fill count has reached the array's capacity, having advanced the cursor the same number of times. At that moment the cursor sits exactly one full array-length past the start of the caller's array, i.e. immediately after the last legitimate slot, not at the base. The helper reports a "too long" parse error and falls into a shared cleanup path whose job is to release any label strings allocated for the entries filled so far. That cleanup loop iterates from zero up to the fill count, but indexes off the (already over-advanced) cursor rather than the caller's original base pointer — so for this specific "ran out of room" case it ends up indexing one entire array-length beyond where the caller's array actually lives on its stack frame. The very first such access — fetching the label-pointer field of the record one position past the array's last element — is the out-of-bounds 8-byte read AddressSanitizer reports: it pulls a pointer value out of adjacent stack memory that was never part of this array, memory which (had the read not already tripped the sanitizer) would next have been handed to a deallocation call as if it were a validly-allocated string pointer. The bug is purely a READ-direction indexing/bookkeeping error in a cleanup routine — it is not triggered by, and does not touch, the numeric sub-identifier values themselves; the overread targets the parser's own internal bookkeeping array, not any heap buffer or attacker-controlled payload data.

The patch is a genuine, minimal, two-part fix sitting exactly on this code path and touches only this one real library source file (parsing logic, not a test or fuzz-harness file, and not a build script). First, immediately after the "too long" error is reported, the fill count is decremented by one, correcting it to the number of entries that were actually completed (the loop's exit condition had left it one too high for this specific exhausted-capacity case). Second, the cleanup loop is changed to use an inclusive upper bound together with the caller's original base pointer instead of the over-advanced cursor. Diffing the vulnerable and fixed source trees confirms this is the entire change: the cleanup now always addresses the correct, in-bounds span of entries whether it was reached via the "too long" fallthrough or via one of the ordinary per-entry parse-error paths earlier in the same loop (which share the same cleanup code and previously suffered an analogous, if less dramatic, off-by-one against the cursor). No unrelated or cosmetic changes are mixed in.
