One-sentence summary: A crafted/corrupted HFS+ image drives the filesystem module's catalog lookup path into a heap-buffer-overflow read when it decodes an embedded, length-prefixed UTF-16 name out of a truncated in-node catalog key without checking the declared length against how many bytes of key data are actually present.

Crash mechanism:
- The fuzz target opens an HFS+ volume image and asks the library to open a file by its metadata (a lookup that resolves an inode/CNID through the volume's catalog structure).
- To find the matching catalog record, the library walks the catalog B-tree, and at each candidate node it must decide whether the record it is looking at is less than, equal to, or greater than the key it is searching for. That decision is made by a case-sensitivity-aware comparison of the two keys' embedded file/folder names.
- Both keys being compared are read directly out of a node buffer that the traversal code allocates just large enough to hold however many bytes it actually read for that particular node from the image on this run (137 bytes in this crash). This is not guaranteed to be as large as the largest key format the on-disk structures allow.
- Each key stores its embedded name as a Pascal-style UTF-16 string: a 16-bit count of UTF-16 code units, followed by that many two-byte code units. The name-comparison logic reads that count field and then loops, reading exactly that many two-byte units straight out of the key's storage -- trusting the on-disk count without ever checking it against how many bytes of the key are actually still inside the node buffer that was allocated for the record being compared.
- Nothing in the call chain from "walk this node's records" down to "compare these two keys' names" carries along how many bytes of the current key are actually backed by real, allocated node data. So when the crafted image supplies a key whose declared UTF-16 count is large enough that reading that many code units runs past the end of the small node allocation, nothing catches it.
- The comparison loop consequently reads one byte past the end of the 137-byte node buffer while decoding the final code unit of the oversized name -- a 1-byte heap-buffer-overflow read, caught immediately by AddressSanitizer. It is a read-only overflow; on a non-sanitized build it would silently pull adjacent heap bytes into the name comparison rather than crash outright.

Trigger conditions (mechanism-level, not byte-exact): an HFS+ catalog B-tree node containing a key whose length-prefixed embedded name field declares a UTF-16 character count large enough that "count * 2 bytes" exceeds the number of bytes actually available for that key within the node buffer read from the image, encountered while resolving a catalog lookup that reaches the case-comparison-driven key-matching logic (e.g. opening a file by its catalog entry).

Fix verification: the recorded fix commit is a single, coordinated hardening pass across four files spanning exactly the areas this bug touches: the core catalog/extents traversal code, the directory-listing code, the Unicode name-comparison code, and the shared header declaring the internal per-record callback interface used by the catalog walk. The specific comparison routine this crash's stack identifies is changed to take an explicit "bytes actually available for this key" parameter, threaded in from the B-tree walk that already knows the real key length for the record being visited. A new check is inserted immediately before the declared UTF-16 count is trusted: if that count would require reading more bytes than were actually supplied for the key, the routine now returns an error/"less-than" sentinel instead of continuing to read. This sits directly in front of, and directly guards, the exact read loop this crash's own stack shows overflowing.

fix_commit_plausible: yes, high confidence. The new parameter and bounds check land exactly on the function named in this crash's top stack frame, and the value being validated (declared embedded-name length vs. bytes actually available for the key) is precisely the value whose lack of validation produces this crash's out-of-bounds read. The patch does not touch unrelated code paths for this crash -- every hunk in the diff is either this exact fix or one of a small number of sibling bounds checks added to other callback sites sharing the same previously-unvalidated-length pattern.
