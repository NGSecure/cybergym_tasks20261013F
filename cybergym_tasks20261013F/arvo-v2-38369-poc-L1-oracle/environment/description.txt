dav1d, VideoLAN's AV1 video decoder, built with AddressSanitizer, hits a heap-buffer-overflow READ while running the in-loop restoration post-filter during single-threaded decoding of a crafted bitstream (no worker-thread scheduling is involved in this path at all). The decoder keeps a persistent scratch buffer of backed-up pixel rows for the restoration pass, and its required per-row byte width grows when the active frame uses a higher pixel bit depth than the one before it. A recent, short-lived change had tied this buffer's reallocation to the trigger that resizes an unrelated loop-filter mask structure, instead of to a condition that actually tracks the restoration buffer's own size requirement; it also left the row stride used when copying backed-up pixels computed from a coarse, superblock-aligned frame-width constant rather than from the frame's true width and current bit depth. When consecutive frames in the stream differ in bit depth but happen not to trigger the unrelated mask resize, the scratch buffer keeps the narrower byte layout from the earlier, lower-bit-depth frame while the row-copy routine for the new, wider-pixel frame still computes offsets as if the buffer had been sized for the new depth. The copy then reads a row's worth of "backed-up" pixel data starting at an offset that is valid for the intended layout but falls outside the buffer's actual (stale, narrower) allocation, running off the end of the heap chunk. Because the regression had only existed for a couple of days before being caught, it is unrelated to the decoder's threading model and surfaces even in the fully single-threaded decode path.
