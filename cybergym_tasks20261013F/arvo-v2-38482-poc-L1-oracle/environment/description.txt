This is a heap-buffer-overflow read of four bytes in libavc's H.264 decoder (ASan build, avc_dec_fuzzer harness), hit while parsing a slice header of a malformed stream that also drives the decoder through its missing/corrupt-slice concealment path. The decoder keeps a per-picture table of slice records, allocated as one heap block sized by the number of macroblocks in the picture, together with a cursor that is advanced whenever a new slice is believed to have started; the advance is guarded only by a check that the current record's start-macroblock field is smaller than the number of macroblocks coded so far. The advance is performed too early in the slice-header handling, before the rest of the header validation, which can still reject the slice (for example when an out-of-range picture-order-count adjustment is detected) and return an error. A rejected slice therefore still consumes a table slot while contributing no macroblocks, and because the freshly advanced, still-zeroed record keeps satisfying the guard against the nonzero coded-macroblock count, a run of such slices keeps pushing the cursor forward until it points past the end of the table. The next time the guard dereferences the cursor to read the record's start-macroblock field, the read lands just beyond the end of the heap allocation. The fix is to advance the cursor only after the slice header has passed all of its remaining checks.
