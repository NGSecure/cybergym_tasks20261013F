wasm3's libFuzzer harness parses and compiles a WebAssembly module's bytecode; compiling a function body dispatches on each instruction's opcode, and for the 0xFC-prefixed "extended opcode" family the compiler does a second-level lookup keyed on the byte following the 0xFC prefix, into a table that only has entries for a small, fixed set of implemented extended opcodes at low byte values. Any 0xFC-prefixed instruction whose following byte falls outside that implemented range fails the lookup, and the dispatch code immediately reads a handler-function-pointer field out of whatever the lookup returned -- without first checking that the lookup actually succeeded -- then unconditionally calls through it. Because the failed-lookup case was never validated, the value read and invoked is indeterminate, so under an optimized ASan build the resulting indirect call does not reliably fault at the dispatch site itself; instead it jumps into whatever code happens to sit at that indeterminate address. The sanitizer's own allocation/free history for this crash makes the consequence unusually explicit: it shows that exact extended-opcode dispatch call site as the direct, immediate caller of the runtime's module-teardown routine -- i.e. the wild indirect call landed on, or immediately reached, the code that walks every loaded module and frees it -- and this runs while the current fuzzer iteration's own module is still mid-compilation and still in use. That premature teardown frees the module object out from under the compiler that still needs it; nothing in a normal, well-formed compile could legitimately reach the teardown routine from there, so this is a direct symptom of the wild call rather than a separate defect in the teardown logic itself. The fault the sanitizer actually reports fires later, when the fuzz harness performs its own end-of-iteration cleanup of the whole embedding runtime and walks the (already-corrupted) module bookkeeping again -- reading a node that was freed moments earlier during compilation, i.e. a heap-use-after-free read.

Fix verification: the fix commit adds exactly one missing check at the extended-opcode second-level dispatch site -- before reading and calling through the handler-function-pointer field, it now verifies the table lookup actually returned a valid entry and throws a clean "unknown opcode" compile error otherwise. The PoC's function body contains a 0xFC extended-opcode prefix immediately followed by a byte value well outside the small implemented range, i.e. exactly the malformed shape that produces the wild call whose effects are visible in this crash's own allocation history. With the guard in place, compilation aborts cleanly instead of taking that wild jump, so the premature module-teardown -- and the later use-after-free it causes -- never happens. The same commit separately gates a module's start-function execution behind a fuzzing-only build flag; that change affects a different, execution-time code path unrelated to this crash (which never reaches actual module execution -- it faults during compilation-triggered teardown and at final harness cleanup), so it plays no role in fixing this specific bug. fix_commit_plausible: yes (high confidence, and unusually well-evidenced) -- the sanitizer's own free-history directly names the extended-opcode dispatch site as the immediate caller of the module-teardown code, which is only explicable as a wild/corrupted indirect call through the exact function-pointer field the added guard now validates.

Independence note: this id shares its fix_commit with two other wasm3 ids from the same OSS-Fuzz disclosure batch (all three regressed and were verified-fixed within the same few-day windows). All three PoCs are distinct byte sequences (different sizes and content) with distinct OSS-Fuzz crash-state / dedup signatures -- this one: heap-use-after-free surfacing at runtime teardown; the others: an allocator wild-read while resizing linear memory, and a wild read during a length/index decode -- so they are independently-reported bugs, not duplicate testcases. All three PoCs nonetheless share the same 0xFC-prefix-plus-out-of-range-byte pattern and are best explained as different downstream manifestations of the same single unguarded-dispatch root cause, which is why one commit's single-line guard closes all three -- this id's own allocation/free history is in fact the clearest direct evidence of that shared mechanism among the three.
