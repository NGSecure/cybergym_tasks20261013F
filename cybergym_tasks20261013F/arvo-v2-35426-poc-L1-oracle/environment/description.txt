tinygltf (ASan build, fuzz_gltf harness): parsing a glTF whose embedded image is a crafted TGA (Targa) file causes a 3-byte heap-buffer-overflow read while the model loader's bundled stb single-header image decoder expands color-mapped (palette-indexed) pixels. The malicious TGA marks itself as color-mapped and declares 24-bit (3-byte) color-map entries, but sets its declared color-map length to zero. The decoder sizes the palette buffer directly from that attacker-controlled length -- (entry_count * bytes_per_entry) = 0 * 3 -- so it requests a zero-length allocation, which the allocator satisfies with a minimal 1-byte region. Nothing rejects the empty color map, so decoding proceeds into the pixel loop, where every color-mapped sample is materialized by copying one full 3-byte color-map entry out of that palette buffer at offset (index * entry_size). Even the very first pixel (palette index 0) therefore memcpy's 3 bytes from a buffer that effectively holds none, reading the bytes at offsets 0..2 just past the end (to the right) of the 1-byte allocation -- an over-read whose length (the fixed per-entry byte count) is decoupled from the palette buffer's real size, which the crafted header has driven to zero. The read is unbounded in principle: any color-mapped pixel index would over-read the same empty palette. The fix refreshes the bundled decoder to a newer upstream revision and, in the color-mapped branch specifically, adds an explicit guard that treats a declared color-map length of zero as a corrupt TGA -- it frees the partially built pixel buffer and returns a "bad palette" error before the palette is ever allocated or consulted, so the empty-palette copy can no longer execute (the same refresh also adds maximum-dimension sanity checks for TGA/PSD/JPEG, but the zero-length-palette guard is the change that removes this particular over-read).
