wasm3's libFuzzer harness parses and compiles a WebAssembly module's bytecode; compiling a function body dispatches on each instruction's opcode, and for the 0xFC-prefixed "extended opcode" family the compiler does a second-level lookup keyed on the byte following the 0xFC prefix, into a table that only has entries for a small, fixed set of implemented extended opcodes at low byte values. Any 0xFC-prefixed instruction whose following byte falls outside that implemented range fails the lookup, and the dispatch code immediately reads a handler-function-pointer field out of whatever the lookup returned -- without first checking that the lookup actually succeeded -- then unconditionally calls through it. Because the failed-lookup case was never validated, the value read and invoked is indeterminate rather than a safely-checked NULL, so under an optimized ASan build the resulting indirect call does not reliably fault at the dispatch site itself; instead execution runs whatever code happens to sit at that indeterminate address, and the crash that actually surfaces depends on what the wild jump lands near for a given input. In this crash the wild jump's downstream effect corrupts state that later gets consumed while the module's initial linear-memory pages are being allocated/resized: the pointer handed to the allocator's realloc-style entry point is no longer a value the allocator's own bookkeeping recognizes, so the sanitizer's allocator-internal metadata read on that pointer takes a wild-address fault ("SEGV on unknown address", classified wild-addr-read) several frames away from the actual defective dispatch site.

Fix verification: the fix commit adds exactly one missing check at the extended-opcode second-level dispatch site -- before reading and calling through the handler-function-pointer field, it now verifies the table lookup actually returned a valid entry and throws a clean "unknown opcode" compile error otherwise. The PoC's function body contains a 0xFC extended-opcode prefix immediately followed by a byte value far outside the small implemented range, i.e. exactly the malformed shape the added guard rejects; with the guard in place, compilation aborts cleanly at that point and the wild indirect call -- and the corrupted allocator state it produces -- never happens. The same commit separately gates a module's start-function execution behind a fuzzing-only build flag (skipping it entirely under the fuzz harness); that change touches a different, execution-time code path this PoC never reaches (the crash happens purely during compilation, before any code from the module would run), so it plays no role in fixing this specific crash. fix_commit_plausible: yes (high confidence) -- the fixed dispatch site is exactly the one named as an intermediate frame in this bug's own OSS-Fuzz "Crash State", and the PoC bytes contain the precise malformed-extended-opcode pattern the guard targets.

Independence note: this id shares its fix_commit with two other wasm3 ids from the same OSS-Fuzz disclosure batch (all three regressed and were verified-fixed within the same few-day windows). All three have distinct PoC byte sequences (different sizes and content) and distinct OSS-Fuzz crash-state / dedup signatures -- this one: allocator wild-read while resizing linear memory; the others: a wild out-of-bounds read during a length/index decode, and a heap-use-after-free surfacing at runtime teardown. They are independently-reported bugs, not duplicate testcases of one another -- but all three PoCs independently contain the same 0xFC-prefix-plus-out-of-range-byte pattern, and are best explained as different downstream manifestations of the exact same single unguarded-dispatch root cause described above, which is why one commit's single-line guard closes all three at once.
