Project: libexif, exercised through its EXIF/MakerNote parser on a crafted image. ASan reports a 1-byte heap-buffer-overflow READ.

Mechanism (re-derived from the crash trace and the vulnerable source, not copied from the crash fields): the crash is not really inside the low-level fixed-width value accessor that ASan blames — that accessor just reads however many bytes its caller asks for. The real defect is two steps further up the same Apple-MakerNote path. After the loader walks the declared entry table into an internal per-entry struct array, each entry's own data buffer is allocated to exactly "declared format size x declared component count" bytes, computed from the (attacker-controlled) entry header, and the entry's bytes are copied into that correctly-sized allocation — so the allocation itself is not undersized relative to what was actually copied in. The bug surfaces later: when higher-level code renders a human-readable value for one specific recognized tag, it unconditionally treats that tag's stored data as a fixed 4-byte signed-integer quantity, without first checking that the entry's own declared format/size actually amount to a 4-byte value. A crafted entry that uses this recognized tag's numeric ID but declares a narrower (e.g. 1-byte) format therefore gets a correspondingly tiny per-entry allocation; converting "its" value still reads a full 4 bytes from that undersized buffer, running a few bytes past the end of the allocation — the observed OOB READ. Direction: a READ past the end of a per-entry heap allocation that was sized correctly for the bytes copied into it, but is later read assuming a wider, hard-coded type than what the entry actually declared; no write, and the raw input/source buffer is not involved at this point (unlike the sibling task below).

Fix: the upstream commit adds, exactly at the point where this tag's value is converted, explicit checks that the entry's stored size is at least 4 bytes and that its declared format/component-count really do amount to a single 4-byte signed value before doing the narrow conversion — returning no value instead of reading past the allocation when they don't. fix_commit judgment: eb452f533b is the correct commit — its tree contains precisely this guard, directly on this task's own crash path — but the recorded patch.diff artifact under this id's materials is an incomplete capture of that commit: it only carries the maker-note loader/table-walk hunks (the under-counted per-entry stride fix and the loader-side bounds checks), and omits the separate hunk, in the separate source file that renders a tag's value, which is the actual fix for *this* crash. Dedup check against the sibling task that shipped from this same fix commit (crash_function exif_get_sshort, OOB read of the raw MakerNote input buffer during the initial table-walk, caused by the under-counted stride in the up-front size check): that is a different buffer (raw input vs. a per-entry heap allocation), a different call path (the table-walk itself vs. a later value-rendering step reached only for one specific tag), and is closed by a different hunk in a different file than the one that actually fixes this crash. Not a duplicate — keep both.
