Summary: A heap-use-after-free (8-byte read) in SerenityOS's LibJS is triggered while evaluating a JavaScript array literal whose element expressions provoke a garbage-collection cycle that frees the not-yet-rooted Array object mid-evaluation.

Root cause: When executing an array-literal expression, LibJS first allocates a JS::Array cell on the managed heap and only afterwards evaluates each element expression before appending the computed values into the array's indexed-property storage. In this input the element values are produced by deeply nested binary "+" expressions whose operand conversions call into Array.prototype.toString / ordinary_to_primitive / to_numeric; those conversion helpers allocate further managed cells (e.g. a LexicalEnvironment), and a cell allocation request drives JS::Heap::collect_garbage. Because the freshly created Array is not yet reachable from any GC root while its elements are still being computed, the garbage collector's sweep_dead_cells pass treats the Array's HeapBlock as dead and frees the whole block. When array-literal execution then resumes and calls IndexedProperties::append -> array_like_size, it dereferences the owning pointer to the freed array's IndexedPropertyStorage, reading 8 bytes out of the already-freed heap region. The bug is a GC-lifetime / rooting defect: a live-but-unreachable object is collected while control is still inside the code that will use it again, not a container capacity or bounds problem.
