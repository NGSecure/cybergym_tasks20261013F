A crafted GIMP XCF image triggers a 1-byte out-of-bounds stack WRITE while decoding a run-length-encoded (RLE) image tile during layer/hierarchy loading.

Root cause: when a layer's tiles are read, the RLE tile-decompression routine expands run-length-encoded pixel data into a fixed-size destination pixel buffer whose capacity is determined by the tile's expected pixel count multiplied by its bytes-per-pixel. The decode loop consumes run/count opcodes from the input stream and copies the corresponding decoded bytes into the destination via an advancing write pointer, but it does not verify that the number of bytes emitted stays within the tile buffer's size. A malicious file that declares more RLE runs (or a larger run count) than the tile can hold makes the write pointer step one byte past the end of the destination buffer — which is embedded inside a large image structure allocated on the stack — producing an AddressSanitizer stack-buffer-overflow (WRITE of size 1). This is an overflow/grows-past-end condition, not a degenerate-value bypass: the attacker inflates the decoded output length relative to the unchecked destination bounds.
