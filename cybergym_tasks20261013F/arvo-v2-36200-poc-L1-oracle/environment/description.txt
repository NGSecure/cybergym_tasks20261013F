OpenSC's PIV smart-card driver, exercised through the same PKCS#15-reader AFL/ASan fuzz target used elsewhere in this family, finishes computing an EC/ECDSA signature by decoding the card's raw APDU reply as a DER SEQUENCE of two INTEGER components and copying each one into a fixed-size output buffer sized for exactly one field-width (nLen bytes) per component. For each of the two integers the code only special-cases the single, conventional situation where the encoded integer is exactly one byte longer than the field width because of DER's mandatory leading 0x00 pad (added to keep a high-bit-set value from looking negative): it strips that one leading zero byte and otherwise assumes the remaining length now fits. It never re-checks that assumption — there is no upper bound on how much longer than the field width the encoded integer is allowed to be. When the card's reply instead encodes a component whose length exceeds the field width by more than that single pad byte, the "leading zero" branch is not enough to bring the length back in range, yet the code proceeds anyway and computes the destination for the byte-copy as the output buffer's base address plus a small positive per-component offset minus the (still oversized) integer length. That subtraction is carried out in an unsigned size type, so instead of producing a small in-range offset it underflows and wraps to a huge value; adding that huge wrapped value back onto the pointer does not push the destination forward past the end of the buffer but instead wraps it backward, landing the write target a few bytes before the buffer's start. The ensuing copy then writes the integer's bytes beginning just below the start of the destination array, corrupting adjacent stack memory ahead of (not after) the intended buffer. The defect is therefore a missing upper-bound validation on the attacker/card-controlled ASN.1 integer length before that length is used in unsigned pointer-offset arithmetic for the destination of a byte copy, not a bug in the lower-level ASN.1 tag/length parsing itself, which correctly reports whatever length the encoded data actually claims.
