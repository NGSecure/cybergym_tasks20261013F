wolfMQTT's client-side packet-wait/dispatch core -- the code every blocking request-then-wait operation (connect, subscribe, unsubscribe, publish-with-ack) funnels through to decide whether a just-received packet satisfies the response the caller is blocked on -- compares the awaited packet type against the type actually received, and additionally treats the two as equivalent whenever neither one happens to belong to a particular family of publish-acknowledgment packet types; that second condition is written as an equality test between two boolean classification results, so it is satisfied not only when both sides genuinely are members of that family but also whenever both sides simply are not, which is a different and much weaker claim than "this is the response we asked for". During the initial handshake, the client sends its CONNECT request and blocks waiting for the broker's connect-acknowledgment, having set aside a small, fixed-size structure for it -- the trailing field of a heap-allocated connection-request object supplied for the whole handshake. In this crash the first packet that actually arrives is of a different, unrelated type (here, a subscription-acknowledgment reply), likewise outside the publish-acknowledgment family, so the flawed check lets it through as if it were the awaited connect-acknowledgment. The dispatcher then decodes that unrelated, larger-layout packet straight into the undersized acknowledgment field, and because that field sits at the very end of its enclosing heap allocation, the single out-of-bounds byte the decoder writes lands just past the end of the whole allocation. AddressSanitizer reports this as a one-byte heap-buffer-overflow write immediately adjacent to the allocation's redzone. The fix, which tightens the equivalence check so that two packets outside the publish-acknowledgment family are no longer automatically treated as matching, is a direct and well-supported match for this crash: it is precisely the overly permissive comparison that lets a reply of the wrong type be decoded into a destination object sized for a different, smaller packet.
