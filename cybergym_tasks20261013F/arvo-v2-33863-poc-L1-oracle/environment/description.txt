OpenThread CLI "dataset securitypolicy" handler (cli-received-fuzzer, UBSan build): the routine that parses the security-policy sub-command is supposed to require two CLI tokens -- a 16-bit rotation-time value and a flag-character string -- before it touches the second one, but the guard that's meant to enforce this only checks that at least one argument is present, which is trivially true anyway since the rotation-time value has already been parsed out of the first argument slot by the time the check runs; it never actually verifies that a second token was supplied. When the CLI line supplies only the rotation-time argument and omits the flags string, execution falls through this no-op guard and unconditionally starts scanning characters from the *next* argument slot's C-string accessor. That slot lies past the number of arguments the CLI line parser actually populated, so the read lands on stale/uninitialized argument state instead of a real string, producing a SEGV read at a small, non-canonical address. Fix verification: the replacement commit tightens the argument-count guard to require at least two tokens before the flags string is dereferenced, which matches the intended two-token grammar and directly closes the single-argument path that reaches the out-of-range slot; OSS-Fuzz's own ClusterFuzz report for this issue records the identical crash address and was auto-verified fixed once this commit landed upstream. fix_commit_plausible = yes.
