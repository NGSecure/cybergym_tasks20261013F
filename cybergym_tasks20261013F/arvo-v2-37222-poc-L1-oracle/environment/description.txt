libexif's Apple-vendor MakerNote decoder, reached while the library loads a JPEG/Exif blob and dispatches the vendor-specific MakerNote sub-parser, treats Apple's proprietary MakerNote payload as a small IFD-style tag table embedded inside the larger Exif marker buffer that was handed to it together with that buffer's total byte length. For each tag entry the decoder reads a 2-byte type code and a 4-byte component count directly from the untrusted entry bytes and multiplies them to get the tag's data size; whenever that computed size is larger than four bytes, the decoder treats the entry's trailing 4-byte field — also read straight out of the untrusted buffer — not as an inline value but as a byte offset into that same shared buffer, pointing at wherever the tag's actual payload is supposed to live. It then allocates a brand-new heap buffer sized to exactly the computed data size and copies that many bytes out of the shared Exif buffer, starting at the computed offset, into the new allocation. Both the offset and the size going into that copy are derived entirely from attacker-controlled bytes of the entry, and nothing is checked beforehand to confirm that offset-plus-size still falls within the bounds of the overall buffer that was originally supplied. The destination allocation is always sized correctly for the copy, so the write side is safe; but when a crafted entry's offset/size pair runs past the end of the source buffer, the copy's read side walks off the end of it, pulling in whatever heap memory happens to sit immediately afterward. The result is a heap-buffer-overflow READ on the incoming MakerNote/Exif data buffer, caused purely by an unchecked attacker-controlled offset+length pair for one tag entry, not by any problem with how the freshly allocated per-tag buffer itself is sized or released.
