espeak-ng's SSML-driven text-to-phoneme pipeline (ssml-fuzzer harness, ASan build): as each word in a clause is translated, its resulting phonemes are appended to a fixed-capacity global phoneme-list array, with a running count tracking how many entries are currently in use. The per-word translation loop that appends to this array had no check tying how many more words it would process to how much room remained in the phoneme list -- multiple internal append points inside a single word's translation could each add several more phonemes without confirming capacity first. After translation finishes, a later post-processing pass walks the phoneme list up to the running entry count to apply pronunciation substitutions; when that count has been pushed past the array's true declared capacity by the unbounded per-word loop, this walk reads entries that were never actually written inside the array's memory, producing the observed out-of-bounds global read. Feeding a clause built from an extremely long run of words that each carry their own embedded voice-control markup is what drives the running count far enough past capacity to reach this walked-off-the-end position. The fix adds explicit remaining-capacity checks to the per-clause and per-word loops that grow this phoneme list, so word processing now stops before the running count can be pushed past what the array can safely hold.
