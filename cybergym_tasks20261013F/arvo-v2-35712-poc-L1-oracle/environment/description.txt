mruby's bytecode interpreter, when fed a compiled script through the protobuf-driven fuzz harness, trips a heap-buffer-overflow read of 4 bytes landing nearly a kilobyte past the end of a tiny internal allocation. Root cause: the interpreter's instruction-dispatch loop handles most opcodes through a straightforward fetch-and-execute sequence that, right before running each opcode's body, keeps the current call frame's saved instruction-pointer field pointing at the instruction actually about to run. A handful of less-common opcodes are instead reached indirectly, through one of three "extended encoding" prefix opcodes that first consume an extra prefix byte and then jump into the very same shared per-opcode body code used by the direct path — but, unlike the direct path, these three prefix handlers never refresh the call frame's saved instruction-pointer field to the operand location they just fetched, leaving it pointing at the earlier, pre-prefix spot. Any opcode body that happens to run via one of these prefixes therefore executes with a call frame whose recorded "current instruction" bookkeeping is stale. Later in the same run, after an attribute-assignment on an object forces an unrelated internal table to grow and be reallocated, something reads back through that stale per-frame bookkeeping expecting it to describe a valid offset into one of the interpreter's own internal data tables; because the value is stale rather than reflecting where execution actually is, the computed offset lands far outside the small table that now occupies that memory, and the resulting read runs straight past its bounds.
