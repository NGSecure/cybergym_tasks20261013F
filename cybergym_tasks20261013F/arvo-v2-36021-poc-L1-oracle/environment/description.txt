SleuthKit's APFS pool/volume parser, exercised through the fls APFS fuzz target, ASan build: opening an APFS pool walks the pool's object map, an on-disk B-tree whose nodes hold a table of fixed-size key/value slots plus a small table-of-contents describing where each slot's key and value bytes sit inside the node's own storage buffer. The generic B-tree-node iterator used to materialize a given slot computes two raw pointers directly from offset fields taken out of that on-disk table of contents -- one by adding a key-offset to the node's key-table base pointer, the other by subtracting a value-offset from the node's value-table base pointer -- and then dereferences whichever of the two it needs (for an interior node, the value pointer is read to get the child block number to descend into) without ever checking that either derived pointer still lands inside the node's own backing allocation. Because the offset fields come straight from the on-disk node content, a crafted container image can set the value-offset large enough that the resulting pointer runs past the end of the node's heap buffer; the iterator then reads a couple of bytes starting at that out-of-bounds address while still constructing the pool object, producing a heap-buffer-overflow read. The defect is a missing bounds check on an attacker-influenced offset before it is turned into a pointer and dereferenced inside the slot-materialization step of the B-tree iterator -- nothing about how the pool itself is opened, or about any unrelated parsing stage, is at fault.
