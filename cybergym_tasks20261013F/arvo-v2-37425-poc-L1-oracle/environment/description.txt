HarfBuzz's font-subsetting fuzz entry point (ASan build), on the path that builds a subsetting plan from a parsed font and needs its own private copy of one of the library's codepoint-bookkeeping sets. These low-level set/map containers are heap-allocated through a generic creation helper; when that helper cannot obtain memory for a brand-new container, it falls back to handing back a pointer to a single, process-wide, permanently-shared "nothing here" placeholder object that every part of the library receives whenever this kind of allocation fails. That placeholder must never actually be mutated: any code about to write into a freshly "created" container is only safe if it first checks the container's own internal "did my last allocation attempt succeed" bookkeeping flag, which is permanently false on the placeholder, before touching any of its fields. To make the private copy, the subset-plan path creates a destination container and then calls the container's own clone/assign routine on it; that routine does correctly consult this flag before copying over the bulk bit-vector storage, so the expensive array copy is properly skipped whenever the destination turns out to be the shared placeholder -- but it then goes on, unconditionally and without re-checking that same flag, to also copy one extra small piece of per-container state (a boolean "sense" bit layered on top of the bit-vector, used to represent logically-inverted sets compactly) straight into the destination object regardless of whether the bulk copy ran at all. When the destination is the shared placeholder, this second, seemingly trivial field write still lands in memory that the process has no business mutating, and it is this stray secondary write -- not the (correctly guarded) bulk copy -- that produces the observed wild-address write/crash. The same unguarded-secondary-write shape recurred across several sibling whole-container operations (copy/union/intersect/subtract/symmetric-difference/invert/clear) on two related low-level container families, and a couple of their higher-level public entry points separately still carried an older, narrower "is this object literally the one known shared placeholder instance" check that only covers calls made through that specific entry point, not calls that reach the same clone/assign logic via an internal route that bypasses it, which is exactly the route this fuzz target's call chain takes. The fix is the correct, forward-direction patch for this defect: every one of the affected whole-container operations gains a guard that skips the secondary state write once the "did my last allocation succeed" flag is already false, and in the sibling container family the equivalent protection is consolidated down into the shared low-level helper that those operations funnel through, while the old entry-point-only placeholder check -- which never covered the internal route and had become redundant with the lower-level guard -- is retired; the change is purely additive/guard-insertion, touches exactly the structures named in the crash's own call stack, and does not alter any other behavior, so it is a fix rather than a regression.
