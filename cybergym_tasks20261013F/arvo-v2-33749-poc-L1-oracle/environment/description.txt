wasm3's libFuzzer harness parses and compiles a WebAssembly module's bytecode; compiling a function body dispatches on each instruction's opcode, and for the 0xFC-prefixed "extended opcode" family the compiler does a second-level lookup keyed on the byte following the 0xFC prefix, into a table that only has entries for a small, fixed set of implemented extended opcodes at low byte values. Any 0xFC-prefixed instruction whose following byte falls outside that implemented range fails the lookup, and the dispatch code immediately reads a handler-function-pointer field out of whatever the lookup returned -- without first checking that the lookup actually succeeded -- then unconditionally calls through it. Because the failed-lookup case was never validated, the value read and invoked is indeterminate rather than a safely-checked NULL, so under an optimized ASan build the resulting indirect call does not reliably fault at the dispatch site itself; instead it runs whatever code happens to sit at that indeterminate address, and the crash actually observed depends on what that wild jump lands near. In this crash the wild jump's effects surface while decoding a LEB128-encoded length/index value during the module's element-segment initialization step: the byte-stream cursor and/or end-of-buffer bound used by that decode end up derived from corrupted/uninitialized state left by the earlier wild jump, so the byte-by-byte decoding loop walks straight past the actual end of the input buffer and takes a wild-address read fault deep inside generic length-decoding code that has nothing to do with element-segment parsing in a well-formed run.

Fix verification: the fix commit adds exactly one missing check at the extended-opcode second-level dispatch site -- before reading and calling through the handler-function-pointer field, it now verifies the table lookup actually returned a valid entry and throws a clean "unknown opcode" compile error otherwise. The PoC's function body contains a 0xFC extended-opcode prefix immediately followed by a byte value well outside the small implemented range, i.e. exactly the malformed shape the added guard rejects; with the guard in place, compilation aborts cleanly at that point and the downstream decode call chain that faults is never reached. The same commit also gates a module's start-function execution behind a fuzzing-only build flag (skipped entirely under the fuzz harness); that change affects a different, execution-time code path this PoC never reaches (the crash happens purely during compilation), so it is unrelated to fixing this specific crash. fix_commit_plausible: yes (high confidence) -- this bug's own OSS-Fuzz "Crash State" names the extended-opcode dispatcher as an intermediate frame directly above the point of failure, matching exactly the site the added guard closes.

Independence note: this id shares its fix_commit with two other wasm3 ids from the same OSS-Fuzz disclosure batch (all three regressed and were verified-fixed within the same few-day windows). All three PoCs are distinct byte sequences (different sizes and content) with distinct OSS-Fuzz crash-state / dedup signatures -- this one: wild read during a length/index decode; the others: an allocator wild-read while resizing linear memory, and a heap-use-after-free surfacing at runtime teardown -- so they are independently-reported bugs, not duplicate testcases. All three PoCs nonetheless share the same 0xFC-prefix-plus-out-of-range-byte pattern and are best explained as different downstream manifestations of the same single unguarded-dispatch root cause, which is why one commit's single-line guard closes all three.
