One-sentence summary: DuckDB's SQL-text parsing fuzzer hits a 1-byte stack-buffer-overflow READ while building a human-readable "here is where the syntax error is" diagnostic for a query whose very last bytes are a truncated, invalid multi-byte UTF-8 sequence.

Crash mechanism:
- The fuzz target hands raw bytes straight to the parser's top-level "parse this SQL text into statements" entry point. Nothing beyond parsing ever runs for this crash -- there is no binding, planning, or execution anywhere on the call path; the entire crash happens inside the parse step itself.
- The supplied bytes are not valid SQL, so the parser raises a syntax error. Before that error is returned to the caller, the parser builds a friendly diagnostic that echoes back the offending query text together with a position marker, so it must walk the query string one displayable character at a time (correctly honoring multi-byte UTF-8 encoding) to line the marker up with the right byte.
- That walk decodes one codepoint at a time: it inspects a byte's high bits to see whether it is a single-byte character or the lead byte of a multi-byte sequence, and if the latter, how many trailing "continuation" bytes it is supposed to consume next.
- The crafted input ends with a byte pattern that looks exactly like the lead byte of a multi-byte codepoint, but the query string simply ends right there -- the continuation bytes the decoder expects to follow never actually exist within the buffer.
- Because the number of continuation bytes to consume is derived purely from the lead byte's bit pattern, with nothing checking that many bytes are actually still available before the end of the buffer, the decoder reads one byte past the end of the query-text buffer trying to fetch a continuation byte that isn't there.
- AddressSanitizer catches this as a narrow 1-byte stack-buffer-overflow read: the overrun lands in the stack redzone immediately following the local string object that holds the harness's copy of the query text.

Trigger conditions (mechanism-level, not byte-exact): a query string that (a) is invalid SQL, so the syntax-error/diagnostic-formatting path actually fires, and (b) ends with a byte that begins a multi-byte UTF-8 codepoint but has no room left in the buffer for the continuation byte(s) that codepoint requires.

Fix verification / fix_commit_plausible: No (or at best highly doubtful) -- the recorded fix commit does not sit on this crash's call path. This crash's entire stack trace is confined to the parser's "turn query text into statements" routine and the UTF-8-aware diagnostic-formatting helper it calls when that fails; neither ever invokes the binder, the query planner, or any subquery-decorrelation/optimizer logic. The recorded fix commit, by contrast, only adds handling for one specific logical-plan-operator case inside the planner's correlated-subquery push-down routine (rejecting a particular operator shape with a clean error instead of an internal-error fallback), plus a regression test for that planning-time error -- machinery that only runs well after a query has already been fully parsed, on a code path this crash never reaches. The original report (2021-05-13) and the "verified fixed" confirmation (2022-09-16/17) are separated by roughly 16 months, and this project is known to have OSS-Fuzz fix-commit attribution drift from day-granularity build bisection (the bisector finds the daily build snapshot where the crash stops reproducing and blames whatever commit is tagged for that snapshot, which need not be the commit that actually touches the crashing code). The empirical vul-crashes/fix-doesn't differential recorded for this id is plausible on its own terms, but most likely reflects some other, unrecorded commit landing in the same daily build window that actually hardened the UTF-8 decoding/diagnostic-formatting path -- not the recorded commit itself.
