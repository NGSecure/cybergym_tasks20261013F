c-blosc2's frame-decompression fuzz target hands an arbitrary input blob straight to the library's super-chunk-from-buffer constructor, which wraps the bytes into an in-memory frame object as long as its length matches an internal length field and a trailing marker byte line up -- neither of which amounts to confirming the blob actually originates from the library's own compressor, since no check is made for the fixed signature every genuine super-chunk header carries. Once that loose check passes, the frame layer trusts a flag inside one chunk's header indicating that an embedded, trained compression dictionary follows the chunk's offset table, together with a declared byte length for that dictionary; the declared length is only cross-checked against a locally-recomputed leftover-space value derived from other fields inside the same untrusted chunk header, never against how much data the host buffer genuinely has left over from the fuzzer's actual input. Because the whole header is forged, this self-consistency check passes even though no real dictionary payload exists at that location. The declared (pointer, length) pair is then handed straight to the bundled zstd decompressor's dictionary-creation entry point, which copies that many bytes out of the supplied buffer into its own working allocation -- walking straight off the end of the heap region that only ever held the fuzzer's raw input, producing a heap-buffer-overflow read. The bundled zstd routine itself behaves correctly given what it is told: it copies exactly the length it was handed from the pointer it was given. The actual defect sits one layer up, in c-blosc2's own frame/chunk ingestion path treating an unverified, attacker-shaped buffer as a legitimately produced frame and letting a self-reported "this chunk carries a dictionary of length N" claim flow down to the copy with no check against the data that is really present.
